## Loader and BDAE evidence

These are available through the existing source resolver when `AssetCatalog` is rooted at `port/android-native/app/src/main/assets`. `content_path_candidates` retains the authored resource URI, then adds the compiled-asset flat folders including `animations/<basename>` and `models/<basename>`; `find_case_path` resolves path components case-insensitively. Thus each class-table clip URI resolves to the exact `animations/` leaf above, and the source weapon URI (`data/3d/characters/prince/weapons/MC_RWeapon_*.bdae`) resolves to its exact `models/` leaf. No rename or alias substitution is needed. The Windows `windows-shared-assets` test root is only a partial corpus and does not contain these leaves.

`frontend/preview/creation_preview.cpp` resolves the authored idle/select URIs into two separate `CharacterVisualConfig::clips` paths. `CharacterVisual::load` reads and loads each clip BDAE independently from the body BDAE. The body `prince_modular.bdae` has zero `animation` and zero `animation_clip` library entries, so its embedded libraries cannot satisfy the six authored class clips. Each standalone class clip is a valid BRES with one `animation_clip` entry named `AUTO_SceneAnims_Range` and 26–31 animation tracks; its filename is selected by the class-table URI, not by an embedded body-library alias.

The body BDAE has 173 controller entries. The exact source aliases needed by the class starter rows are present: `MC_Head__naked-mesh-skin`, `MC_Torso_default_warrior-mesh-skin`, `MC_Torso_default_rogue-mesh-skin`, `MC_Torso_default_mage-mesh-skin`, and the matching `MC_Feet_default_{warrior,rogue,mage}-mesh-skin` / `MC_Hands_default_{warrior,rogue,mage}-mesh-skin`. These are body-controller aliases, not external files. The source modules resolve their controller and material records from the body BDAE; the Rogue dagger and Mage quarterstaff are separate weapon BDAEs.

## Validation and scope

Compared SHA-256 for each decoded leaf against its member streamed directly from the installed APK. Read BRES headers/libraries for the six clips, Android `models/prince_modular.bdae`, and the staged Windows-cache body; confirmed the Android body hash matches the staged body (`7e998e60bdfcbc9237c9867bd8de146f6d59bc9f8c9c028cd4d2391f460f0b3e`, 3,207,072 bytes). The existing recipe test now has a `--require-all-appearance-assets` mode, and `run_runtime_creation_appearance_asset_resolution_tests.ps1` accepts the caller's `AssetCatalog` root. Strict LLVM-MinGW build and test passed against `port/android-native/app/src/main/assets`, resolving all eight clip/weapon leaves with exact APK hashes under `animations/` and `models/`; the same executable also passed in its legacy mode against `.local-inputs/windows-shared-assets`, preserving that partial-cache missing-leaf report. Build output is isolated at `.local-inputs/equipment-appearance-asset-resolution-tests/`. This proves source-asset availability and resolver/manifest behavior, not class-preview runtime parity or successful rendering in every host.
