# Frontend menu audio session V1

## Original-behavior evidence

- **Visual evidence:** Original v1.0.3 reference frames `.local-inputs/referenceframes/dh2-act1/at-0045s.png` and `at-0060s.png` show the Enter Name and Choose a Class screens. They confirm the menu flow and its visible destinations. These frames do not show a click, sound, or transition timing; no audio is inferred from them. The source caller evidence is recovered from the v1.0.2 `dqmenus_droid.swf`, so a version difference remains possible.
- **Logic evidence:** `port/windows-foundation/features/frontend/flow/authored_navigation_evidence.json` records `root/sprite510` (`menu_MainMenu`), `btn_MENU_SINGLE_PLAYER`, `onRelease` at SWF action offset 291293. After the `FirstTimeClicked` gate the function calls `NativePlaySoundFX("MenuConfirm", 1)` at offset 291328, before the occupied/empty-slot branch; it then pushes `menu_EnterName` at 291424 or starts the game at 291496. This is the sound admission and call-order boundary, not a blanket click cue. Recovered source trace `port/android-native/reports/menu-effects-v4/handoff.md` identifies `NativePlaySoundFX 0x43ae10 -> PlayMenu 0x36bc34 -> Play 0x36b80c`. The exact generated map is `MenuConfirm` ordinal 141 -> XML UID 2 -> `sfx_menu_confirm.wav`; `MenuSelect` ordinal 143 -> UID 3 -> `sfx_menu_select.wav`. The source Play path resolves the exact name; unknown names are no-ops. PlayMenu calls Play with `(id, false, 0, 0, true)`. Disabled/ID/online and datasource readiness gates can skip emitter creation; a miss does not veto the ActionScript menu operation. A fresh emitter uses the original defaults and selected catalog group.
- **Expected behavior:** When the exact recovered `menu_MainMenu / btn_MENU_SINGLE_PLAYER / onRelease` action reaches its sound statement, submit only `MenuConfirm`, retain its generated ordinal/UID identity, and use the caller's actual monotonic event timestamp. Unknown menu actions, missing original samples, and output/focus failures remain diagnostic sound outcomes and do not block menu navigation. The adapter owns one retained native V42/WinMM output for the menu and must shut it down before gameplay audio takes that output.
- **Uncertainties:** The visual frames are v1.0.3 while the recovered action SWF is v1.0.2. The frames cannot establish audible timing or parity. The test proves decoded exact samples reached WinMM's started receipt, not perceptual loudness or parity. No canonical JNI/App callback graph is represented here; integration still requires the frontend owner to call the strict authored-action method in source order and pass actual window focus/minimize state.

## Adapter and caller handoff

New files: `frontend_menu_audio_v1.hpp/.cpp`. `resolve_frontend_authored_menu_sound_v1` maps only the exact recovered menu/button/action tuple and returns expected name/ordinal/UID. `play_authored_menu_action` rechecks that identity against the generated catalog before it submits. `frontend_menu_event_qpc_ns_v1` samples the existing QPC-backed `winmm_monotonic_ns`; for production, prefer the frontend's already paired action timestamp from that same QPC domain. The caller passes actual focus/minimize changes to `window_activity`, pumps receipts on its producer thread, and calls checked `shutdown` before transferring audio ownership. All sound errors are non-vetoing receipts after required runtime initialization; inability to initialize the adapter is a lifecycle integration error.

**Smallest caller hook requested:** In `menu_MainMenu`'s Single Player `onRelease`, immediately after its existing `FirstTimeClicked` guard and synchronously before the occupied/empty-slot decision, call `play_authored_menu_action("menu_MainMenu", "btn_MENU_SINGLE_PLAYER", "onRelease", actual_qpc_ns, receipt, error)`. Ignore nonfatal receipt outcomes for navigation. Refresh `window_activity` from the real frontend window's focus/minimized state, not an elapsed/frame clock. On leaving the menu, checked-shutdown the session before gameplay output initializes. Keep the exact sound assets mounted under the caller's recovered soundpack root. Integration lead owns the actual frontend/main/CMake hook.

## Verification

Focused observable test is `run_frontend_menu_audio_v1_tests.ps1`. It compiles the new adapter with LLVM-MinGW C++17 and opens real WinMM output on a fresh isolated sound root containing hash-checked original samples. It drives the strict Single Player source action and separately verifies MenuSelect, then checks unknown-name/unmapped action no-op, actual focus loss/regain, invalid event time, missing exact MenuSelect WAV (no substitute), and checked close/join/drain.

Latest result: **PASS**. Main-menu `MenuConfirm` ordinal 141 -> UID 2 and MenuSelect ordinal 143 -> UID 3 both decoded and received real WinMM started receipts; QPC/device-clock scheduling, focus pause/resume, no-op, invalid-time and exact-missing-sample branches passed. Audible parity was not measured. This is isolated output verification only; real frontend UI/callback and frozen-preview verification remain pending integration lead.
