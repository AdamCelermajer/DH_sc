# Swamp King encounter plan v1

## Evidence checked before implementation

- **Encounter identity and admission:** the recovered Swamp MGP row is recorded in `reports/fidelity-video-audit-v18.json:1576-1596`. In `bossroom_ruins_ns__8`, `_prim_Boss_SwampKing_01` uses `charpropsname=SwampKing`, `auto_spawn=0`, and `activate_cond=IsBefore_Swamp_Escape`. The population audit had skipped this row because its condition adapter did not know the symbol. The original `v2Conditions` cache resolves it: `IsBefore_Swamp_Escape` has one Quest stub `(op=1, quest-row=50, argument=13)`; the actual `v2Quests` name at row 50 is `Swamp_Escape`; `v2QuestState.PostClosed=13`. `NativeConditionRuntimeV69` factory 1 compares `argument_c > Quest.state0`, so the exact gate is `13 > the same Character's Swamp_Escape state0` (states 0–12 true, PostClosed 13 false). The plan now carries that typed predicate and a small pure evaluator, with actual-cache tests. Production `ObjectBase::TestEnableCondition` remains authoritative: IDA `0x33e6d4` obtains `PlayerManager::GetLocalPlayer(0,true)`, preserves the local Character/Save quest-sync14 early return, checks Level difficulty and the source disable bit, then evaluates embedded ConditionData `+0x8c` when accepted and untested; it calls `SetEnable` and marks tested only when its caller flag requests it. The real `NativeConditionRuntimeV69` and `SourceQuestServiceBinding::quest_state(character,50,-1,...)` already own same-Character/current-difficulty/online collection resolution. The CQPG projection uses the same CharacterState/Quest progress owner and explicit collection/difficulty, while actor admission remains on the native condition path. The normal MGP initialization owner calls `InitPost` then `TestEnableCondition(false)` in `ObjectInitializationV1` phase 3 (`port/level-loader/object_initialization_v1.cpp`); IDA `ObjectManager::Spawn` `0x34b724` separately calls `TestEnableCondition(true)` in its `!a5` branch. Once admitted, `swampking_core.luac` sets its `allowed` flag only after the native AI state compares equal to `AIStates.Idle` (`swampking_OnUpdate`, source line 665), and its range callbacks require `allowed`. The `isAttackReady` function calls `LookAtTarget()` only when `HasTarget()`; target presence does not gate readiness. Readiness requires script state `ST_IDLE`, native AI state not `AIStates.Skill`, and `canDiveNow == false` (source lines 210-222). The live source/script facts remain typed owner inputs.
- **Phase/attack rows:** `.local-inputs/character-script-assets-v1/bootstrap-cache/data/scripts/ai/swampking_core.luac` is readable recovered Lua source despite its `.luac` filename. Its source rows define phase 2 at `HPPercentCurr <= 75` and the weak animation flag at `<=25`; both are one-shot flags (`swampking_OnUpdate`, lines 634-648). Phase 1 close-range first attack is `DoSkill(1)`; subsequent rolls `<80` choose slot 1, otherwise slot 0 (`swampking_OnTargetInCloseRange` lines 614-627; `Do_MeleeAttackPhase1` lines 264-282). Phase 2 close attack uses first-attack roll `<50` for slot 0, otherwise slot 1; later rolls `<40` call slot 0 and rolls `>40 && <90` call slot 1. The source has no catch-all for roll 40 or 90–100, so this plan preserves the no-dispatch result. Both ranged phases ultimately use `DoSkill(2)`; phase 1 enters the intimidate animation first and dispatches on its end callback, while phase 2 calls slot 2 directly. The specific mappings from `DoSkill` slot numbers to the five named skill files are **not established** and the API does not make them up.
- **Authored skill sources/tables:** the five files `swamp_king_attack_1.luac` through `_4.luac` and `swampking_atk_spit.luac` provide source IDs and targeting details. The first four cite class rows `SwampKingSkill5PCT` (300 range, single target), `SwampKingSkill30PCT` (200, single target), `SwampKingSkillPoisonAttack` (400, target-list poison effect), and `SwampKingSkillAOEPushback` (400, shockwave/target-list). Spit uses dynamic `CharacterProperties.RangeMaxDistance`, a 250-unit AOE search, and `SwampKingSkillPoisonAttack`/`SwampKingSkillPoisonAttackAOE` class rows plus a timer trap. The class row names were checked against `.local-inputs/class-tables-parsed.json`; the files and fields are also asserted by the source test. The plan keeps named skill files separate from the opaque `DoSkill` slot selectors.
- **Dive transitions:** the source uses a 15,000 ms dive timer, retries after 500 ms while the native state is not Idle, and starts an 8,500 ms repeating dive-pattern timer. Dive animation end schedules position relocation after 500 ms, emerge after 1,000 ms, and retarget after 3,000 ms. Emerge completion reaches `DiveAttackDecision` after 500 ms; the decision allows two dive iterations before resetting its counter and returning to Idle. Emerge entry also requests `DoSkill(3)`. These source events, timers, gates, and slots are represented as plan rows/fields only; no native AI/animation/timer execution is claimed.
- **Original video:** I inspected the supplied v1.0.3 Part 1 reference at 15:00, 15:08, 15:16, and 15:32. At 15:08 the visible target name is **BOGWOMP**; by 15:16 that target is down and the player receives `+75 Gold`; 15:32 shows an Emerald Slime. This is direct evidence for those ordinary water-area encounters, not a Swamp King phase demonstration. Separately, the existing individually inspected 357.5–357.8s frames read **TRUNGUS**, not a boss. No inspected frame proves the Swamp King's phase, dive, death, or reward behavior; the v1.0.3/v1.0.2 asset-version difference also remains unresolved.

## Reusable behavior and API

`runtime_boss_encounter_plan_v1.hpp` exposes one immutable `EncounterPlan`, the recovered `QuestStatePredicate`, exact source attack decisions for close/ranged callbacks, and source transition rows. `evaluate_swamp_king_activation_from_quest_progress_v1` now binds this predicate to the existing portable `CharacterQuestProgressV1` owner: callers first load/decode the same profile's `CharacterState.source_quest_progress_cqpg` through `RuntimeQuestMenuV1::load_progress_from_character` (or that owner's `decode`), then supply its source collection and current difficulty. The helper verifies the original table still has `Swamp_Escape` at row 50 and calls `CharacterQuestProgressV1::query(character, {collection,difficulty,50}, ...)`; the existing owner rejects a different CharacterState identity and unknown/uninitialized buckets. It adds no quest state storage, schema, or raw state callback at the boss-plan boundary. The native `ObjectBase::TestEnableCondition`/`NativeConditionRuntimeV69` caller still owns actual actor admission; this helper is the same-profile CQPG-backed predicate projection, not a native condition graph or an integrated encounter claim. A caller still needs the actual HP percentage and AI state and must dispatch callbacks through existing owners. There is no source-faithful basis here for a synthetic boss actor, skill-slot-to-script mapping, progression result, or reward continuation.

`runtime_boss_encounter_session_v1.hpp` adds `SwampKingSessionConsumerV1`. A caller binds the exact SwampKing ActorId in its current `CombatSession`, then composes `on_frame_begin` into that Session's existing frame-begin lane. It checks same-session actor/lifetime leases and source actor ID on each typed input. After the admitted actor's native AI state reaches Idle, it starts the actual repeating 1,500 ms attack-readiness timer; each firing uses the source gates `SK_STATE == ST_IDLE`, native state not Skill, and `!canDiveNow`. `HasTarget` is not a readiness gate. The same frame owner latches phase 2 at `HPPercentCurr <= 75` and clears attack readiness exactly as `swampking_OnUpdate` does. Source HP, admission, `SK_STATE`, `canDiveNow`, native Idle, and native Skill remain typed facts from their exact owner; the feature invents no AI or script state. The timer does not dispatch an attack or dive.

The phase threshold itself has no authored animation transition. SwampKing's original melee binding defines `SwampKing_Idle` (sequence 672, looping) with animation row 1328 rooted at `data/3D/characters/swampking/animations/swampking_idle.bdae`; the same asset is loaded into the retained test Session actor. The Lua `OnEndOfAnim` callbacks are specifically for Dive, Emerge, and Intimidate flags. They are not consumed by the phase/timer behavior, so the consumer does not substitute them or dispatch unsupported anim-dictionary clips. The `swampking_hurt_01.bdae` source Injured clip is present but has no bindable tracks against the retained SwampKing model. The native test fixture omits only that unrelated Injured state from a decoded copy of the source binding, retaining the original actor/model/property row and exact Idle row. The session test seeds live Session HP because original HP initialization is not owned by this helper; the source HP percentage and native AI facts are passed as typed inputs. This gives same-Session consumer evidence, not complete actor/native-character initialization.

## Focused verification

`run_runtime_boss_encounter_plan_v1_tests.ps1` builds and runs the helper with strict C++17 warnings (the existing `quest_persistence_v51.cpp` provider source emits three downgraded pre-existing missing-field-initializer warnings), then checks the actual population row, raw `v2Conditions` and `v2Quests` cache rows, `PostClosed` constant, native comparison/caller source, AI gates and branches, all five skill sources, and five actual class-table rows. It decodes the original retained Quest table, initializes one named Character's existing quest-progress owner, writes state 12 for `Swamp_Escape`, encodes/loads that same profile's CQPG bytes, and proves the bound gate true; it then repeats with state 13 and proves false. Wrong Character identity, unknown progress, and out-of-range difficulty fail closed. It also tests the pure source predicate across all 14 source constants, phase threshold boundaries, first and repeated close attacks, each phase-2 missing-branch boundary, invalid rolls, ranged transitions, and the dive/animation constants.

`run_runtime_boss_encounter_session_v1_tests.ps1` builds a separate Windows native test against the existing read-only foundation archives and the pinned LLVM-MinGW compiler. It loads the actual SwampKing binding/property/Idle root, confirms the BDAE bytes and source sequence/animation row, and runs `SwampKingSessionConsumerV1` from the same `CombatSession` frame-begin callback. Tests cover exact 1,500 ms cadence, repeating callback count, Idle admission, phase-2 one-way transition at 75%, ready false for source Skill/script/dive gates, ready true without a target, foreign actor facts, duplicate frame callback, and retained Idle pose continuity. The test fixture excludes the unrelated Injury row because its BDAE has no bindable tracks; it does not test Injury visuals, native AI execution, or a complete SwampKing runtime.

Result: **PASS** for the isolated helper, same-Character CQPG provider binding, same-CombatSession phase/timer consumer, and original-source/table assertions. The session consumer is not wired into the Windows campaign/native Character AI. Live actor admission, full SwampKing animation/fight behavior, death, progression, and rewards remain unverified.
