# Mesh buffer ownership and draw callers

This note extends [`../buffers/ANALYSIS.md`](https://github.com/Noamcelermajer/DH_sc/blob/e6da25b83086ea01fb1d4cd46ae12da3bbac645f/port/engine-rendering/buffers/ANALYSIS.md) with the callers and owners around `CMeshBuffer`. The buffer note covers `IBuffer` internals, dirty upload, vertex binding, and GLES draw calls. This note follows a mesh buffer from construction into scene-node submission and through its immediate reference releases.

## Binary evidence

The source is the APK member `lib/armeabi-v7a/libDungeonHunter2.so` (15,938,284 bytes; SHA-256 `36498eb8180ffb74759e6305e9596db999f18583d460f3b8534abcb6022f5e80`) from APK SHA-256 `32c2d027b585a42547311cd95da6a3975fdb3174e663e513d42a7f49d1a4c200`. [`original-functions.json`](original-functions.json) records 22 exact function ranges (7,668 bytes total) and 10 four-byte supporting vtable words, including ELF file offsets, PT_LOAD segment indices, and SHA-256 hashes. [`reference/original-functions.asm`](reference/original-functions.asm) contains their ARM-mode listings. The selected byte rows and data words were compared byte-for-byte with the corresponding APK ELF PT_LOAD bytes; all 22 function ranges and 10 words matched.

## Construction and stream-buffer references

`collada::CMesh` construction at `0x00645588` iterates source mesh buffers. For each, it allocates a 56-byte runtime `scene::CMeshBuffer` and calls its constructor at `0x006bd9f8` (`0x00645948`–`0x0064597c`). The resulting intrusive reference is stored in the Collada mesh's per-buffer record. The selected constructor walks the source stream descriptions and calls internal `addStream` at `0x006bccf0` for the stream paths it accepts.

`addStream` at `0x006bccf0` first branches on the `SMesh` mode at `SMesh+0`. Its buffer-cache behavior differs by mode; the earlier generic “cache absent” description was too broad.

For mode 1, used by every recovered type-0 BDAE mesh, `[SMesh+8]` points to the shared interleaved descriptor. `addStream` reads that descriptor's runtime-buffer cache at `+40`. A non-null cache is reference-counted and copied into the emitted stream record. If it is null, `addStream` follows the descriptor's layout arrays and emits a stream record with a null buffer; this branch returns without calling `createBuffer`. The serialized cache word is zero in the recovered mode-1 descriptors.

`CMeshBuffer` construction at `0x006bd9f8` is the mode-1 descriptor-cache producer. Its **final boolean parameter is separate from the factory's sharing boolean**. On a null descriptor `+40` cache, both final-boolean branches create an `IBuffer` and store it at descriptor `+40`: the false branch passes the object reached through descriptor `+36` and byte count `SMesh.vertexCount * descriptor.stride` to the driver's `createBuffer` slot (`0x006be40c`–`0x006be454`); the true branch treats descriptor `+36` as a refcounted owner, retains it, passes `owner+0x0c` and the same computed byte count to `createBuffer`, and stores the result (`0x006be204`–`0x006be2e8`). The function range is 2,680 bytes with SHA-256 `175e56defbf9666c5cb012f976f63d79989b717a03b354c6543a0ab70b48a551`, and its full byte-matched listing is in the manifest reference. Which constructor-boolean path a specific asset takes is not established; the file-backed `descriptor+36` field is observed either as vertex bytes or as an on-demand record offset, and its runtime representation is not fully resolved.

The factory's separate `CColladaFactory::isSharingMeshBuffers` helper at `0x0062ff38` (8 bytes; SHA-256 `007f34a6c3441b0240da53f253e513b959105da2d8803255e1856aa48f48db47`) returns 1. `CColladaFactory::createGeometry` passes that result to `collada::CMesh`; `CMesh` uses it to reuse an existing geometry-side buffer object at record `+0x34`, or constructs a `CMeshBuffer` when that object is absent (`0x006457e0`–`0x0064597c`). This factory-level choice does not suppress the `CMeshBuffer` descriptor-cache producer when construction is needed. The factory callsite and hash are recorded in the [geometry-route audit](https://github.com/Noamcelermajer/DH_sc/blob/e6da25b83086ea01fb1d4cd46ae12da3bbac645f/port/asset-geometry-type1/untyped-indirect-sweep/ANALYSIS.md). The traced loader/draw route contains no second mode-1 producer; resource release can clear the cache, while runtime call ordering and branch values remain unobserved.

For mode 0, `[SMesh+8] + 20*streamRef` selects a separate per-attribute source record. Its cache is at `+16`. On the cache-miss path, `addStream` dispatches through the video-driver vptr at displacement `+0x78` (`0x006bcef0`–`0x006bcef8`) and stores the returned `IBuffer` back into that per-attribute cache. The corresponding `COpenGLES2Driver` vtable word at `0x00977b98` contains `0x005b13f4`, the inherited `CCommonGLDriver::createBuffer` entry. The vtable word address is symbol-relative `+0x80`, accounting for the two-word Itanium vtable prefix before the object's vptr address point. This creates the engine buffer object; its OpenGL name is still lazy, as described in the buffer note.

The constructor calls `CVertexStreams::setupStreams` at `0x005a178c`, which installs eligible emitted stream records and takes the references used by draw setup. The complete source-record lifetime is still unavailable, so the immediate cache and stream references do not establish when every `IBuffer` is finally released.

The mode-0 trace shows a cache-backed reference in a source stream description as well as references held by the mesh-buffer stream set. Mode 1 can reuse an existing descriptor cache, emit a null buffer from `addStream` when the cache remains empty, or populate that cache through either constructor-final-boolean branch. Neither path includes enough of the source object's complete lifetime to establish exactly when every cached reference is released. As a result, destroying a `CMeshBuffer` alone does not prove that its `IBuffer` reaches zero references.

## Scene mesh and material submission

`scene::CMesh::addMeshBuffer` at `0x006bc664` increments references for a `CMeshBuffer`, `CMaterial`, and `CMaterialVertexAttributeMap`, then pushes the record into its buffer vector. The record destructor at `0x006bbe18` releases those three references; `scene::CMesh` destruction at `0x006bc248` destroys the vector. The Collada mesh has a parallel per-buffer record: its record destructor at `0x00644c88` releases the same three kinds of references, and the mesh destructor at `0x00644cfc` destroys the record vector and its database subobject.

Both selected mesh-node render functions use the mesh interface to enumerate buffers and retrieve each buffer, material, and attribute map. Relevant vtable words are listed in the manifest for `scene::CMesh` and `collada::CMesh`. `scene::CMeshSceneNode::render` at `0x00585370` and `collada::CMeshSceneNode::render` at `0x00646730` call `IVideoDriver::setMaterial` (`0x0035eb10`) with the material and attribute map, then `IVideoDriver::drawMeshBuffer` (`0x0035ebd0`) with the mesh-buffer reference. The downstream driver dispatch, `setupArrays`, buffer binding, dirty upload, and primitive draw are documented in [`../buffers/ANALYSIS.md`](https://github.com/Noamcelermajer/DH_sc/blob/e6da25b83086ea01fb1d4cd46ae12da3bbac645f/port/engine-rendering/buffers/ANALYSIS.md) and the parent rendering note.

## Release path and limits

`scene::CMeshBuffer::~CMeshBuffer` at `0x006bc8c4` releases its stream-set object at `this + 0x14`; if that set's final reference is dropped, it calls `CVertexStreams::~CVertexStreams` at `0x005a0a1c`. The latter walks 16-byte stream records and drops each record's first-word `IBuffer` reference. Other buffer members are released in the mesh-buffer destructor as well. The immediate releases are visible; they do not establish final `IBuffer` deletion when a source-side cached reference remains.

The buffer note follows final `CBuffer` cleanup to `glDeleteBuffers`, and shows update through `glBufferData` or `glBufferSubData` when the buffer is bound. This owner trace does not identify which gameplay-side mutation marks a particular mesh buffer dirty, nor does it establish context/thread ownership, context-loss behavior, or the full source-cache destruction path. The `CMeshBuffer` `onDelete` forwarding body was excluded because the identity of the member it invokes was not resolved. Vtable and class names are bounded symbol/dispatch identifications; serialized mesh fields and all runtime enum meanings are outside this trace.

No build or tests were run for this analysis package.
