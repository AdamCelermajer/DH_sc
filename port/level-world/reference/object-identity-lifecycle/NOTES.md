## Identity and handle ownership

`ObjectManager::GetObjectByPtr`340c54 is not a manager search. It default-constructs a12-byte handle33f50c (`key0,cached0,frameUINT_MAX`); nonnull object invokes GetHandle33dd2c and copies the result. The supplied manager argument is unused; GetHandle reads the global manager's frame at+78. GetHandle first stamps object+2c's shared handle frame, then copies all12bytes. Key and cached object are unchanged. `ObjectHandle(ObjectBase*)`33f524 has the same null/default and nonnull GetHandle behavior. The new native helper takes the actual global frame explicitly; it does not pretend a different manager instance controls that source call.

ObjectBase C1 33f15c allocates its shared handle at+2c, default-constructs it, then stores `this` in cached+4. The new object still has key0, so `GetObject`33fdc0 returns null until registration. The original constructor writes disabled81=0, updating85=0 and visible8a=1; it does **not** initialize byte82 in this captured body. Do not treat Flags8 as a reconstructed ObjectBase constructor.

The existing `character_target_providers` handle resolver already proves actual source RB insertion/lookup/cache behavior. Key0 always resolves null. Nonnull cached pointer and matching frame bypass the map; otherwise map operator[] can insert an empty record and refreshes the local handle's cache/frame. Shared cached pointer is not refreshed by that path. Stamping the shared frame before copying can make its old cached pointer current. This new module preserves that behavior and does not add a fresh registry lookup.

Object registration is a separate producer. Add34b270 first queries GetObjectByName34aca0. An existing name result destroys the incoming object via virtual+4 and returns the existing handle. For a new result it writes record.object+18, increments manager+50, installs the handle into object+2c, sets strings/network fields, classifies via source virtuals, and appends Character to manager+60. GetObjectByName's allocation branch34afd8..34aff4 takes and increments manager+4c. Its complete body also supports special name/player/network scopes. These bodies are captured/read, but no native complete Add/name-lookup parity claim is made. An arbitrary numeric actor index is not a recovered object handle key producer.

Lua uses a different identity path. Frozen `_GetTarget`3b6c7c reads raw Character+408; Value7 nonnull becomes a fresh table with `_this` lightuserdata and shared per-class registry metatable. Value7 null becomes nil. `_GetID`38ebe4 returns raw receiver pointer as Value2/lightuserdata. Neither path resolves a handle, performs RTTI conversion nor holds an actor alive. The frozen `script_object_bridge` source-method dispatcher performs normal `_this` table lookup and captures that pointer before projecting arguments. Therefore table equality is not actor equality, and `defender:GetID()==GetID()` compares the same full native receiver identity.

## Deferred deletion and actual removal evidence

`ObjectBase::Delete`33ddb4 stores byte82=2 then disabled81=1. `setUpdating`33dcf0 writes the low argument byte to85. Neither frees or removes an object. MarkForDeletion3432f8 scans the exact ordered pointer list at manager+3c; existing identity is unchanged; otherwise a12-byte node is allocated and appended. Null identity is accepted by this low-level list routine. Native DeletionQueue16 is the logical ordered list projection, not source intrusive-node storage.

ObjectManager.Update34a620 splices pending+34 into active+2c, processes deletion+3c, then iterates active objects. At34ab20 a nonzero delay82 is decremented and the object remains queued; at zero it calls removal policy. The active pass queues disabled objects via MarkForDeletion and detaches their active node (34a9e0..34aa0c). Thus the deletion countdown is serviced at manager update boundaries, not elapsed milliseconds. Full Update/network/pause/profiler/room ownership is captured/read only.
