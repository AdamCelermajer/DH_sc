# Attack query and acquisition dependencies

These are new original-only captures and probes. The supplied ELF is SHA256 `36498eb8180ffb74759e6305e9596db999f18583d460f3b8534abcb6022f5e80`. Six capture groups (`reference`, `helpers`, `leaf`, `reader`, `producer`, `equipment`) bind37 routines. `dependency-probes.json` records1,591 original cases:1,322 inventory parameter queries from real decoded ItemTable rows,45 full original AI/equipment radius combinations, and224 original geometric-body cases. In addition, the full original AIProps record reader executes all76 bundled rows. There are zero mismatches, native comparisons=0. The new script is `tests/prince_attack_services_discovery.py`.

## Equipment and radius producers

`ItemInventory::CanMeleeAttack(int&)` at `0x3fff30` calls actual inventory virtual+8 (`0x400014`→HasRangedWeapon). A ranged main-hand type4/5 returns false without changing its output. Otherwise it selects `GetCurrentEquipSet(1)`, follows the equipment vector/set/main-hand reference/item instance, and writes Item row+`0x9c`, Param5, or0 for an absent main-hand reference. It returns true in that melee case. This is a distinct overload from no-output `CanMeleeAttack()` at `0x3ffd38`, which returns the low byte of the ranged predicate XOR1.

`ItemInventory::CanRangeAttack(int&,int&,int&)` at `0x3ffebc` repeats the genuine ranged predicate. False retains all three caller outputs. True follows the selected main-hand item and writes row+`0x98/+0x9c/+0xa0` (Param4/5/6). The probe populates original runtime rows from the source-derived ITM1 corpus, SHA256 `5aa7b428b2031dd88c1b533e47e06bada2b372c92211240bbd64d88a73119db9`; actual GetItem and inventory lookup instructions execute. It does not substitute a supplied equipment capability boolean. This proof reuses the earlier full ItemTable reader's real cache outputs; it does not run that full loader again here.

`AI_GetMeleeRadius` at `0x3d4c34` initializes its output integer0, calls the preceding melee overload (its returned boolean is ignored), resolves actual Character.GetCharAIId `0x3a2fec`, converts the integer to float and adds the selected AIProps runtime row+`0x20`. Character cached property index1 (owner+`0xffc`) selects a valid AI ID; invalid values use8. The AI row has stride68. The original `AIProps::read` at `0x506f3c` produces every row from actual `ai_pyarray.bin`, SHA256 `bfe56f4a07dbe49bb55543137ae343334082b6a340ca156f367ee51e3b2771bc`. Prince row44's exact melee-radius word is `0x43480000` (200). This is additive authored combat reach, separate from the body radius, rendered AABB and walk speed.

Selected equipment ownership remains a real producer boundary. The captured ItemInventory constructor `0x3ff200` creates the two equipment vectors and nine empty slots for each. `_EquipItemToSlot` at `0x400634` reads inventory references/slotting/item requirements and performs the actual reference assignments. Those captures identify what must feed the borrowed query projection; they are not an implemented native equipment lifetime/mutation system.

## Character range parameters and geometry

The actual Character primary vtable at `0x965f38` binds slot+`0x128` to `CanRangeAttack(int&,int&,int&)` at `0x3a4cd0`. Cached property32, RangeProjectileID, unequal to-1 short-circuits equipment: properties30/31 at owner+`0x1070/+0x1074` undergo signed ASR8 before becoming minimum/maximum integers, and property32 becomes projectile ID. Otherwise it tailcalls the actual inventory ranged overload. The existing no-output native CanRangeAttack query establishes capability only; it does not yet supply these three outputs.

`AI_IsInRange` at `0x3d6604` selects explicit target or live AI+40; absent target returns false. It calls owner virtual+128, requires true, then reads original `GetTargetPosition` for owner and target. It computes `(dx*dx+dy*dy)+dz*dz` in source single-precision order. Minimum/maximum integers are squared with32-bit `MUL` **before** signed integer-to-float conversion. Its two comparisons accept both ends inclusively: `float(int32(min*min)) <= distance² <= float(int32(max*max))`. Therefore a native port must preserve integer overflow/bit interpretation and must not substitute floating squaring or a radius chosen from the body. The224 geometry fixtures directly prove normal min50/max100 boundary inclusivity; arbitrary integer-square overflow is captured source behavior, outside that fixture grid.

`AI_IsInMeleeRange` at `0x3d6188` resolves explicit/current target through ObjectHandle. Only a resolved Character with type word+`0xf4`=0 and its interaction virtual+90 returning8 takes the character melee branch. That branch reads both original target positions, computes the same3D squared distance, and requires `(ownerMelee+targetMelee)^2 > distance²` strictly. The equality boundary100 is rejected. Other targets/interaction types call actual `AI_IsInInteractionRange` at `0x3d4f98`; its result is retained, rather than forcing a melee decision. ObjectHandle's manager lookup/generation cache and full interaction-radius services remain explicit in the geometry probe.

`GetTargetPosition` at `0x3935dc` returns owner+`0x184` only if owner+`0x180` is nonnull and byte+`0x80` is nonzero; otherwise it returns owner+`0x160`. Actor body coordinates cannot automatically stand in for this producer. `GetLookAtVec` at `0x393ae4` uses stored rotation+`0x174` and produces `(sin(rotation),-cos(rotation),0)`.

## Actual acquisition producer

`TargetList::Search(float,float)` at `0x3d0020` constructs a `RoomObjectList` over the global ObjectManager room-object list at manager+`0x80`; it does not query the physics broadphase. Its genuine vtable `0x969d20` routes Reset/AtEnd/Next/Get/GetChar to the captured source methods. `Search(float,float,IObjectList&)` at `0x4a3428` obtains owner GetLookAtVec and GetTargetPosition, then calls the complete search body `0x4a2f34`.

The full body clears prior results and walks the live object list. It rejects null/self objects and byte+`0x8a` disabled objects; applies IsZonable and zoned/in-zone gates; requires target IsInteractive(owner); then runs the character or generic-object validity path. For constructor flags1 and type0 used by melee acquisition, Character validity requires the cached visibility/interaction word gate at reference+`0x1314` against target+`0x1310`, a living target, source AI_IsEnemy, and the source player-pair gate. This cannot be replaced by all live monsters or a nearest-body test.

For each accepted target, it computes full3D center distance, subtracts target interaction radius and reference melee radius, checks the search reach, computes absolute signed angle against the source look vector, and checks the cone. It pushes actual `TargetInfo` records into a priority_queue, not an append-only list. The real record stride is20 bytes: object identity, adjusted distance float, angle float, classification flags, and trailing word. `_sortClosest` at `0x38d570` compares classification bit0 first and then distance; `_sortFrontal` at `0x38d5b4` compares the same bit and then angle. Their heap ordering/ties/nonfinite behavior and object-list membership/lifetimes require their own proof before live binding.

The earlier caller oracle's zero/one search-result fixtures used16-byte mock records because only the first word was consumed. That fixture was not a record-layout reconstruction. The new native attack coordinator borrows an ordered identity array, so its ABI and caller proofs are unaffected; a real provider must preserve source heap result order.

`AI_SetTarget` at `0x3d6890` is also broader than assigning target+40. It always writes candidate+3c. Its false-mode path conditionally clears owner+14d0, writes live target, refreshes last-target and target-change byte+4c, computes target-alive+48 and sight+49 using real predicates. True-mode writes live target while skipping those extra effects. `AI_IsEnemy` at `0x3d574c` uses ObjectHandle Character resolution, actual faction IDs/relationship table and interaction fallbacks. These services remain required to replace the renderer's direct attack event faithfully.

The next safe implementation order is parameter/radius query kernels over genuine decoded AI/item/property inputs, exact geometry over source target-position inputs, then separately proven target interaction/hostility and room-object search/filter/heap ownership. Captured source is not a full live binding, networking implementation, native ObjectSearcher or gameplay parity claim. No existing production/CMake/renderer/ADB edits were made.
