# Bounded read-only GPU/resource growth audit V37

Date: 2026-10-06. No emulator launch, reproduction, heap stress, APK operation, GL execution or production source change was performed for this audit. This is source inspection and saved-event evidence, not a native leak diagnosis.

## Authoritative host evidence

Saved `windows-memory-events-v36.xml` contains four Windows Resource-Exhaustion-Detector Event 2004 records. The 2026-10-05 13:12:54Z record reports system commit 137,157,767,168 bytes against limit 137,261,162,496. It attributes 63,135,215,616 bytes (58.8 GiB) and 139,370 handles to qemu PID154420, and 23,959,715,840 bytes (22.3 GiB) to another qemu PID112372. Earlier records show several simultaneous qemu processes with large commits/handle counts. The 2026-10-06 record has unavailable process attribution (zero/empty entries); it must not be used as proof that no process was responsible. These are host process totals, not Android app malloc totals or individual GL object sizes. The reported loader 64KiB allocation failure is consistent with exhaustion, but its exact saved log was not inspected here.

The XML cannot distinguish emulator/SwiftShader allocation retention, guest RAM backing, driver resources, app-requested objects, Windows handle growth, or multiple concurrent emulator workloads. It supports a hard host commit/handle guard. It does not support claiming an app-native leak.

## Lifecycle contracts requiring explicit monitoring

`SwfGpu::initialize` abandons prior GL names rather than deleting them, and reuploads retained CPU textures. Current Java `MainActivity.onSurfaceCreated` invokes native initialization, which supplies a genuine surface/context creation boundary. This is appropriate for lost-context names. A same-context reinitialization would require a live teardown first; do not generalize initialize into a reload API. `SwfGpu` has no explicit destructor cleanup in the inspected class; current reset paths release bitmap/cache resources while programs/stream/FBO remain reusable for context lifetime. Record initialization/context-generation counts to detect accidental same-context replay.

OriginalUiSession failure reset preserves images when external authored movies still hold leases; this is intentional ownership, not by itself a leak. When external movie count returns zero, verify the reset/lease-release transition actually occurs. Front failure reset clears movies/fonts/leases before reset_images. FX reset/live deactivation and context loss have distinct deletion/discard paths. Do not glDelete old IDs in a replacement context.

No evidence inspected establishes unbounded per-frame CPU queue append. FX current source/queue/index maps are rebuilt/reused for current submissions; old inactive FX records expire. Status/audio/font queues were not comprehensively audited here. They need their own pending-count/byte telemetry if the host guard detects renewed growth.

## Recommended guard and telemetry (not implemented by this report)

1. Keep the external Windows Job commit cap and watchdog mandatory before any further emulator test. Include host qemu commit, handle count, aggregate qemu count, system remaining commit and explicit stop reason. Android-requested GPU bytes cannot bound emulator overhead.
2. Add one admission ledger per actual GL context plus subsystem counters: live/generated/deleted object counts, vertex/index capacity bytes, base+mip texture bytes, FBO/RBO bytes, CPU decoded pixels, pinned encoded assets, shader/reflection bytes, pending queue bytes. Track current/high-water and allocation/reallocation counts; distinguish discard-on-context-loss from live deletes.
3. Start with inspectable configurable limits, not source-game constants: total requested GPU256MiB, texture subbudget128MiB, FX buffers64MiB, SWF cache existing8MiB, individual decoded image64MiB, retained programs256. These are conservative engineering proposals requiring an actual asset census before acceptance. Charge both front/gameplay owners to one context-wide ledger. Driver residency can exceed these values.
4. Enforce checked size multiplication and admission BEFORE CPU resize/decode and BEFORE glBufferData/TexImage/RenderbufferStorage. On failure, return an exact required-resource/budget error and release candidate ownership; do not silently drop gameplay FX or replace textures. Evict only unused resources whose owner leases permit deletion. Active resources must fail admission explicitly rather than bypass all bounds.
5. Request dimensions/mip count from actual asset descriptor; estimate full generated mip chain, not only baseRGBA. Charge VBO capacity (not current visible count), both IBO and retained CPU topology, and both SWF target colors plus shared depth/stencil.
6. Add a bounded rolling counter sample, not per-frame unbounded logging. Future guarded tests should cover context loss, movie reload/font creation, hidden pooled effects, warm resource reuse, target resize and item despawn; compare live counts after teardown. Do not reproduce the58GiB event to establish this.

## Scope and limits

No hardware/driver allocation attribution, native heap snapshot, GL residency query or renewed emulator test was performed. V34 prior fixture proves reduced query/upload/allocation work, not a bound on host qemu memory. The source gaps above can amplify driver pressure and deserve guards; none is sufficient to explain the observed tens of GiB or handle growth without correlated counters. No production change is requested to remove existing finite resource ownership or alter clocks/particles/art.
