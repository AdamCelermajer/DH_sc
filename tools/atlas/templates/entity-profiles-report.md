# Entity profile generator evidence and behavior

## Investigation

This generator is lookup infrastructure: its visible invariant is that an authored entity row leads to its exact table rows, source references, assets, scripts, and explicit reverse owners. It does not alter gameplay and has no direct original gameplay animation to reproduce. No continuous original gameplay clip was used as evidence; the skill verification matrix records source-table and staged-file associations, not a rendered animation sequence.

The recovered consumers establish the link rules used here. `port/game-data/skill_tables.cpp` names the 15 SkillTable fields and decodes each SkillList entry as an indexed skill row. `port/game-data/animation_tables.cpp` decodes animation sequence steps with clip/redirect, FX, sound, and timing members and checks signed references against their respective source tables. `port/game-data/items.cpp` validates the 15 base item fields and 23 item-specific fields; `tools/atlas/table_sites.py` records exact source edges for item `SwooshSoundFX`, `SwooshFX`, `AudioVisualID`, `ModularModule`, and `IconName`. The `AudioVisualID` edge reaches `loot_audiovisual#group0`, whose source fields link pickup/drop sound rows and an authored visual token. `ModularModule` remains an unresolved named component when no exact source reference exists; a coincidentally named file is not promoted to a model edge. `port/game-data/item_power_tables_v5.cpp` and `loot_power_resources_v7.cpp` establish the item-power row schema and nested `SpecialEffect`, `AttrBonusList`, and `AttrMonopoly` data; `loot_power_creation_v7.cpp` is the producer, gated by authored loot entries that reference an item-power list. Item-power relationships are therefore represented as explicit source rows and exact references, with loot/caller admission left to the source root graph.

The caller/admission boundary matters: these rows describe authored lists and values. The skill cast path still checks saved rank, eligibility, readiness, and target conditions; an item audiovisual row does not establish that an item is generated, equipped, dropped, or picked up. The item fidelity audit (`docs/ida-fidelity-audit-2026-10-11/items.md`) records these distinct runtime paths and known live-port gaps. The generator therefore labels links `EXACT_AUTHORED_SOURCE_REFERENCE` and marks runtime use `NOT_INFERRED_FROM_AUTHORED_ASSOCIATION`.

## Item model, drop visual, and icon consumers

`resolve_item_resources(ctx, refs, tables, assets)` emits supplemental `references` and `derived_edges` for consumer relationships that the canonical table reference extractor cannot prove by row/file-name similarity alone. Each edge source uses the stable typed profile ID (`entity:<table>:<index>`); the original canonical row ID is retained separately as `row_id`. Profiles keep only the stable derived edge IDs; the root graph can ingest the edge/reference payloads separately. The helper opens source inputs read-only and does not regenerate atlas outputs.

The original Item record decoder in `port/game-data/reference/items/NOTES.md` places `ModularModule` at byte offset `0x48` and `Name` at `0x4c`; the native projection exposes the latter as `Item.name`. `Character::INV_UpdateSkin` at `0x3a999c` reads the equipped `Item.name`/module, and the recovered `VisualObject::GetModularModuleId` at `0x474568` probes `#<module>-mesh-skin` within its requested category. `VisualObject::SetWeaponSkin` at `0x473cd8` constructs `data/3d/characters/prince/weapons/<name>.bdae`. The caller only takes those weapon branches for its first two equipment slots; this helper consequently creates a weapon asset edge only for the authored `MC_RWeapon_` / `MC_LWeapon_` tokens. It never derives a filename from arbitrary strings.

For body modules, the helper matches the exact generated controller URI as bytes in `character_models_dictionary#group0.Path` BDAEs, then retains each model dictionary row and every `CharacterProperties.ModelFile` owner as a candidate. The association proves source controller-ID presence, not parsed category membership or selected runtime module. Original `CModularSkinnedMesh` construction at `0x649120` applies serialized model defaults without a class input; direct `_InitEquipment` at `0x3b395c` is reached through `InitPost` `0x3b4d60` only for the local player. The original player models contain distinct Warrior/Rogue/Mage controller variants, and the source equipment matrix records the class-specific starting item/controller candidates. No `ModularVisual` enum-to-class mapping is claimed, and NPC model defaults are not replaced by player gear.

`ItemObject::InitOnce` at `0x3ece80` uses the fixed `data/3D/GameObjects/itemdrops.bdae` scene and passes the exact `loot_audiovisual#group0.Visual` token to its source scene consumer. The profile edge points to every exact-path source asset candidate and records whether the exact token string is present in its BRES. The Android asset hash is covered by the existing source-scene receipt; an iOS asset candidate is retained independently and is not assigned that Android receipt. Token presence remains a candidate node lookup; only Potion0[925] (`dummy_itemdrop_Potion`, static authored subtree) and GoldStack01[418] (`root_itemdrop_Gold_01`, controller rest pose) have Android source-scene receipts in `source-world-item-drop-render-v1.json`. No per-token BDAE filename is invented. The original inventory audit reports all 1,322 `IconName` values empty, so empty item icon fields produce an explicit no-icon disposition.

Skill `SkillIcon` labels join to the extracted original `dqcharmenu_droid.swf` sprite 79 label/frame map in `port/windows-foundation/features/skill_ui/source_skill_art.json`. Empty labels select the authored `undefined` label. The SWF target is exposed as `asset_uri: .repo/port/android-native/app/src/main/assets/original-cache/data/menus/dqcharmenu_droid.swf`, matching the asset inventory's `.repo/` path; the extraction catalog path is separate. The SWF hash and sprite/frame are retained; the join does not assert learned or presently displayed state.

Graph integration contract check: the current `tools/atlas/graph.py::add_item_resources` consumes `target.uri`, `target.asset_uri`, and `target.template_uri` through `Index.files()`, plus direct IDs in `target.assets` and `target.models[].asset.id`. Itemdrop edges therefore expose both `template_uri` and a `template_asset` source summary; `template_uri` resolves the Android and iOS asset variants through the graph index, while the nested summary retains the exact asset provenance. Skill icon edges expose the `.repo/` SWF `asset_uri` and explicit `asset_ids`. A read-only `Builder.files()` check resolved the skill SWF, itemdrop template variants, and Longsword model paths. This does not run or modify the full graph integration.

The source reports supply native/recovered-consumer evidence and cache-backed checks for the named examples; this helper itself has no gameplay visual sequence to inspect. The lookup invariants are tested against the exact staged source assets: weapon URI exact/case-fold path resolution, body controller candidate preservation across class owners, itemdrop template/token checks, SWF symbol/frame checks, empty item icons, missing source files, and fields with no value. These checks are isolated source-lookup verification, not integrated browser/runtime visual verification.

Known-answer evidence is in `coordination/v21.8/SKILL-VERIFICATION-MATRIX.md`: Knight BashDown list/skill row 7 resolves animation sequence 347, effect set 164, and sound row 190; GroundSlam row 51 resolves sequence 350, effect set 173, and sound row 185; Charge row 13 resolves sequence 349, effect set 172, and sound row 48. These IDs and file names corroborate source joins. They do not prove continuous runtime timing or a rendered visual result. Item example rows are weapon `loot_table#group3[100]` (`Bow03`) and potion `[925]` (`Potion0`); both have exact audiovisual row edges, while Potion0's `SwooshFX` and `SwooshSoundFX` are `-1` sentinels and should not produce edges.

## Expected behavior and verification

`build(ctx, index=None)` returns one compact profile per skill list and skill row, all 1,322 item rows, item-power lists/rows/monopoly rows, plus faery lists/faeries, projectile definitions/models, effect sets/animated effects, animation sequences/character animation rows/clips, sound rows, and scripts. A profile holds a stable typed ID, source identity/status, scalar root fields, exact field edges, authored reverse owners, joined table/reference/asset IDs, literal-include script closure, and audio asset IDs. Full payloads remain in canonical atlas tables/references/assets; profiles do not copy them. Missing rows, unresolved references, dynamic includes, and negative sentinels remain gaps or absent edges rather than guessed relationships.

Focused observable checks: (1) BashDown row 7 links animation sequence 347, effect set 164, sound row 190, and `sfx_skill_warrior_headsplitter.wav`; GroundSlam row 51 links 350, 173, 185, and `sfx_skill_warrior_earthstrike.wav`; Charge row 13 links 349, 172, 48, and `sfx_skill_warrior_shield_rush.wav`. Each profile also exposes the corresponding source script closure. (2) Bow03 row 100 and Potion0 row 925 link through their exact `AudioVisualID` references; (3) the resource resolver follows Bow03's exact weapon URI, Longsword01's present model asset, and the StartingSuit/Rogue/Mage body controller candidates without choosing a class; (4) Potion0's exact drop token/template is source-verified, while Gold and other tokens retain their distinct levels of evidence; (5) item IconName empties and negative swoosh fields create no guessed relationships; (6) a synthetic missing source row/field remains safe and creates no edge. The run also checks every generated profile ID is unique and that all 1,322 item indices plus all SkillTable and SkillListTable indices are covered. These are isolated generator checks; the integrated atlas build and browser presentation remain the integration lead's responsibility.

## Uncertainties and limits

The captured data may combine platform caches and game versions. Source references establish authored identities, but unresolved component names, dynamic Lua, conditional calls, runtime state, and actual rendering remain uncertain. Body-controller byte presence is not proof of the module's descriptor category; class/basebody matches remain candidates, and original version/platform cache variants may differ. For itemdrop visuals beyond Potion0 and GoldStack01, a BRES string match does not prove the selected scene subtree or its rendered pose. No claim is made that every stored script branch or sound is exercised for every owner. This generator is a source lookup layer; it does not complete runtime verification or certify gameplay fidelity.
