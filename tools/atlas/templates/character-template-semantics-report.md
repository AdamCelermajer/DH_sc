# Character template source links

## Investigation and evidence

This is an Atlas source-linking task. Its output describes authored source relationships and has no direct gameplay visual counterpart; a frame sequence would not establish these static table identities. The expected gameplay invariant, inferred from the recovered table consumer rather than directly observed in footage, is that a template-backed Character placement supplies a named template whose ordered `CharInfo` members feed the existing Character-table selection path. This link report does not claim that a placement spawns or that a particular member is selected at runtime.

The native consumer evidence is the recovered `GetCharPropertiesId` at `0x3b3d38`, called from Character InitPost (`0x3b4d60`, call site `0x3b4e74`). The recovered call prefix checks the once-only `called1394` flag and `spawn_probability274` before reaching it (`port/level-world/character_npc_initpost_owner_v1.cpp:18-29`; original sequence `port/level-world/reference/character-world-npc-initialization-v1/original-function.asm`). The source handler first reuses cached signed-16 `properties_id13c8`; when uncached, a nonempty `char_template` takes precedence over `charpropsname`, whose direct path performs an exact CharacterTable name lookup (`port/level-world/canonical_character_family_v4.cpp:40-47`). The property declarations place `char_template` at `0x1398` and `charpropsname` at `0x13b0` (`port/level-world/canonical_property_declarations_v1.inc:68-69`). The recovered `0x3b3d38` handler does not read either MGP `*_pydata` field; those fields are treated below as authored table-alias relationships, separate from the runtime signed-16 cache.

`CharacterTemplateTableV78` reads ordered `Name` and `CharInfo` fields, stores each authored member list, and looks up an exact template name (`port/game-data/character_templates_v78.cpp:19-21,26-34,42-47`). Its rows expose signed-16 selected IDs; this is why the authored `char_template` key can link to a template row while its sibling `char_template_pydata` selector can only link to the table. The exact authored table aliases `Charater_Templates` and `CharacterTable` appear in the recovered registered-name list (`port/level-world/reference/character-game-design/registered_names.inc`). The port bridge checks these aliases before using `CharacterTemplateTableV78` or `CharacterTable` (`port/windows-foundation/actor_population.cpp:61-80,144-170`); this documents the port's source-to-table contract and is not a claim that native `0x3b3d38` reads the MGP alias field.

The Atlas decode contains 121 Android `character_templates#group0` rows. The iPad package separately exposes a validated names-only group at logical URI `data/pydata/character_templates_pyarraynames.bin`, with 121 unique names; its underlying `file000373.dat` bytes cross-check against the Android names stream. The iPad also has a decoded `character_properties_pyarraynames.bin` names stream with groups of 448, 3 and 4 names. These support `RESOLVED` source-scoped relationships at `LIKELY` confidence: an `ios_source_name` target points to the names-stream asset/group/ordinal/name, and an `ios_table_source` target points to the exact logical names-stream source for a table alias. Neither target contains an Android table/index identity or asserts native IDs. The full dry run covered 4,200 `char_template`, 4,200 `char_template_pydata`, and 344 `charpropsname_pydata` references.

## Expected behavior and implementation

For each exact source `GameObject`, resolve a nonempty `char_template` only when the element says `gametype="Character"`, the source value matches the reference key exactly, and the sibling table selector matches the registered `Charater_Templates` alias. Match that key to one exact Android `CharacterTemplateTableV78` row. Preserve ambiguity with typed candidate row targets and preserve missing names as unresolved. Resolve `char_template_pydata` separately to a table-level target when the same Character source gates hold; never interpret its alias as a template row name. Resolve `charpropsname_pydata` to the `CharacterTable` table only for the direct `charpropsname` path, with no nonempty `char_template` override. The two alias links are static authored alias-to-table relationships documented by the registered-name and port-bridge evidence, not fields consumed by native `0x3b3d38`.

The resolver reads each referenced XML/package asset once, then selects the exact indexed GameObject, and returns a deep copy of the reference list. It preserves existing IDs and uses exact source gates. An iPad exact name plus explicit table alias can point to its matching names-only group entry with status `RESOLVED`, confidence `LIKELY`, and `native_id_verified=false`; this source-scoped target is not an Android row and makes no runtime ID claim. Unknown platforms stay unresolved.

## Uncertainties and remaining gaps

The full in-memory resolver dry run linked 2,161 Android `char_template` rows with `PROVEN` confidence and 2,001 iPad names-only entries with `LIKELY` confidence; 38 stayed unresolved. All 2,173 valid Android and 2,012 iPad `char_template_pydata` aliases linked at their respective confidence levels, while 15 source refs stayed unresolved because duplicate `triggercount` attributes around line 534 make `lighthousse/lh01_lv05_open_03_01.mgp` fail whole-file XML parsing. The 344 `charpropsname_pydata` aliases linked (172 Android `PROVEN`, 172 iPad `LIKELY`) after the direct-name and template-precedence gates. The 38 `char_template` gaps comprise the 15 malformed-source refs, 12 Android exact-name misses, and 11 iPad names-only misses. The missing names include `WaterTemple_Skeletons1` (6 each platform), `IcyCavern_UncommonType1` (2 each), `UW_CommonType3` (2 Android and 1 iPad), `Lighthouse_UncommonType1` (1 each), and `RoyalTombs_UncommonType1` (1 each); no spelling normalization is applied. The iPad corpus has names-only streams but no corresponding decoded `CharInfo` row arrays or native table IDs, so iPad names cannot receive native template row IDs. The iPad source-table alias association remains a port-contract inference with unverified native IDs; recovered `0x3b3d38` does not consume the MGP `*_pydata` property. No visual runtime sequence, actual spawned actor, random member outcome, or completed campaign population is claimed.

## Verification

Before implementation, the focused verification was defined as synthetic XML/table fixtures covering: exact Android row match; table alias distinct from row key; Character gametype and source selector gates; `char_template` precedence over direct CharacterTable lookup; missing and duplicate rows; iPad namespace rejection; stable IDs; and idempotence.

`py -m py_compile tools/atlas/character_template_semantics.py tools/atlas/character_template_checks.py` passed. `character_template_checks.run()` passed all 17 focused checks, including reading the exact indexed XML element, rejecting unknown platforms, and checking source-scoped iPad target shapes. This is isolated resolver verification only. The full in-memory resolver dry run against the current 4,200-reference source ledger produced the counts above without writing shared outputs. Full Atlas regeneration, downstream graph/UI verification, and any runtime/visual check remain outside this bounded helper task.
