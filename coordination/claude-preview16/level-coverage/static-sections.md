## Gaps found, prioritized (general systems; each row names the file that owns it)

P1 (blocks most levels, do first)
1. **Actor profile library.** 375 population notices say `Explicit character profile unavailable` (e.g. InfectedBurned 19, Darkwood_MeleeBandit* 29, Crypt_Ghost 15, DT_Cherub 13, DT_Skydevil 12+6, DT_DarkGuardian 11, FireTemplar_* 22, UW_Hell_Pup 8, TarSlime 8, IH_Snow_Wolf_Hound 8, IH_Yeti 7). `actor-profiles-v2.xml` (package root) is a 26-actor export for Act 1 only. Needed: profiles generated from the original character/animation tables (`data/pydata`, `game-data/character_templates_v78.cpp`, `game-data/animation_tables.cpp`). Owner: P16 host/spawn. Code: `port/windows-foundation/actor_population.cpp:166`, `actor_profiles.cpp`.
2. **Condition policy.** 255 actors are skipped as `Condition policy returned unknown` (`activate_cond`/`deactivate_cond`/`auto_spawn`). The runtime needs the campaign flag/quest condition state and a table of condition names (e.g. `RENE_FOLLOW`). Code: policy lambda in `port/windows-foundation/main.cpp` (population load, ~line 990).
3. **Spawn points and EntryPoints.** 64 notices `requires caller-owned spawning policy`; 112 SpawnPoint declarations on 32 maps. Spawn-from-template at a position is the P16 item 1 system. Note: the player's start is not in the level data; the coverage runs used the first `_prim_EntryPoint*` declared in each map (`level_inventory.cpp`, `spawnText`). The real choice comes from the transition data (TriggerZoneExitLevel + saved level state). Owner: P16 map/spawn.
4. **Classes the Windows EXE does not run.** Most of the authored classes have a canonical implementation in `port/level-loader` or `port/android-native`, but `dh-foundation` compiles none of them (`features/levels/level_class_registry.cpp`, status `ported_elsewhere`): `TriggerZoneExitLevel` (61 decls on 20 maps; level transitions, needed for any multi-level play), `Door` (47 on 15), `AnimatedDecor` (692 on 17; not instanced, so not drawn in the captures), `QuestMoveInZone` (21 on 11), `CheckpointZone` (27 on 9), `Decor` (23 on 3), `TriggerTrap` (9 on 2), `TriggerObject` (6 on 4), `SoundEmitter` (2 on 2). Canonical files: `port/level-loader/catalog_auxiliary_v67.cpp`, `canonical_auxiliary_families_v16.cpp`, `catalog_generic_v70.cpp`, `level_batching_source_v96.cpp`. Every class above also has an original factory address in the ELF registry (`port/level-loader/original_factory_table_v1.inc`, 33 entries), so this is a porting gap, not an unknown class. Owner: P16 host/containers/map (adopt the canonical catalog or port the rows).
5. **Library-only classes** (code exists, not wired to the level runtime): `TriggerZone` (95 on 17 maps; `features/encounters/trigger_constructors.cpp`), `DestructibleContainer` (95 on 10; `features/interactions/session_admitted_destructible_v1.cpp`), `OpenableContainer` (40 on 13; `features/interactions/session_container_admitted_openable_v1.cpp`), `Dummy` (274 on 17; `source_world_objects.cpp`), `SpawnPoint` (see 3). Owner: P16 containers and host.
6. **Full level constructor.** `--source-root-scopes` on 003_darkwood fails: `Source constructor scopes: Level::_LoadFromXML service: required original LoadTemplate assertion(9) provider` (`main.cpp:1440`, `SourceRootScopes::build`). Map-generic, so this is the gate for scripted/trigger behaviour beyond geometry + population. The coverage runs therefore do not use `--source-root-scopes`.

P2 (needed for procedural levels and some fixed maps)
7. **Procedural levels (37 `.rule.xml` maps): the generator is already ported canonically, not in the EXE.** `port/level-loader` has the rule reader, lists, blocks, connections, the original RNG and the layout generator: `procedural_rules_v1`, `procedural_lists_v1` (35 rule files, 171 declarations, 479 elements compared), `procedural_random_v1` (1,378 cases against the original ARM code), `procedural_layout_v1` (`generate_procedural_layout_v1`: all 70 authored runs match the original hierarchy, selections, coordinates and height bits). Its README says procedural rendering and generated module assembly are still unverified, and nothing outside the procedural files calls `generate_procedural_layout_v1`. The Windows EXE has no procedural path at all. Remaining work, sized medium: (a) link the canonical procedural files into `dh-foundation` (or a shared library), (b) assemble each generated tile from its gameplay/visual MGP/MVP through the same module path as fixed maps (`load_level` + `load_actor_definitions`), (c) verify tile placement against original footage. Start from `port/level-loader/README.md` (lines 73-170) and `reports/` (procedural milestone handoffs).
8. **Module node missing (103, 117).** `original_scene.cpp:54` throws `Original module node missing`. Both are debug maps whose authored node names are absent from the module .bdae (content mismatch). Decision for root: skip such a module with a logged notice instead of aborting the whole level.
9. **Module-less levels (108).** `level_manifest.cpp:149` throws `Level XML contains no authored modules`. A level with actors but no geometry should load with a notice.
10. **LevelConfig absent (20 debug maps).** The camera loader threw `Selected level has no LevelConfig` for every map without a LevelConfig (`original_camera_config.cpp`). Fixed locally: the original InitPost camera defaults are used and one notice is logged. Unverified against the original for these maps; flagged in the code comment.

## Coverage run recipe (reproducible)

- Inventory: `level_inventory.exe --root <levels-root> --package <package assets> --android <Android files> --table <Android files/data/pydata> --out inventory.json --md inventory.md` (source `features/levels/level_inventory.cpp`, target `level_inventory`).
- Runs: `runs/batch3/<id>.args` = `base.args` (generic KnightPlayerBase + `--start-mode swamp` + `--profiles` + `--original-camera` + `--move` + `--fixed-step 0.0333`) + `--position <first EntryPoint>` + `--level data/scene/<id>.mlx --frames 30 --capture <id>.ppm`; jobs run with `port/windows-foundation/tools/quiet_run.ps1 -Parallel 8`.
- Report: `level-coverage/make_level_coverage.sh inventory.md <batch dir> <out dir>`.
- Caveat: `quiet_run.ps1` leaves a `dh-foundation.exe` process behind after some runs; check `Get-Process dh-foundation` for the build path before rebuilding (we killed two stray processes).
