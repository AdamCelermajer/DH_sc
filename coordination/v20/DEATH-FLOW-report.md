## IDA / recovered logic

The IDA export `.local-inputs/ida-apk-export-2026-10-07/libraries/libDungeonHunter2.so` is APK v1.0.2, while videos are v1.0.3; version differences remain possible.

- `PlayerManager::Update` 0x378fb4 calls `_CheckLocalDeaths` 0x376100 and `_CheckGlobalDeaths` 0x375eb4. Local gate: current Level exists and source lifecycle/state field+304 equals 38 (the export does not establish that this field is a semantic “type”); local player has a Character; its virtual +52 dead predicate is true; manager phase +433 is positive. `_HandleLocalDeaths` is 0x375fe8.
- `_HandleLocalDeaths` offline: if `menu_FadeToBlackScreen` is not visible, push it once and mute FX. Online: use state +1809 and the local death timer/HUD; expiry hides the timer and calls `ReviveLocalPlayers(...,0)` without offline checkpoint reload.
- `NativeReviveAllPlayers` 0x43b1e4 requires the current Level source lifecycle/state field+304 == 38. Online it sets manager +1816 and returns. Offline it pops `menu_FadeToBlackScreen`, pushes `menu_FadeFromBlackScreen`, then calls `ReviveLocalPlayers(...,0)`. The SWF registers it through MenuManager's native registration path.
- `NativeScreenIsBlack` 0x439fa4 does not inspect pixels; online it advances manager +1812 from 1 to 2. `NativePlayPreviousMusic` 0x43ad58 calls `RestartMusic(0)`.
- Offline `ReviveLocalPlayers` 0x37565c restores FX volume, calls `Level::LoadCheckpoint`, clears Character buffs, restores non-origin revive coordinates, calls `Character::Revive(...,1)`, sets Idle, ensures `CharacterDesign.MinimumPotionsOnDeath`, then stops current music and starts Level music with a 1000 ms fade. The SWF's later previous-music call is distinct and must remain distinct.
- `Character::Revive` 0x3a59ac initializes HP/MP via `_InitHpMp`, marks alive, initializes its physical object, floor-corrects position offline and updates skills.
- Checkpoint production is a distinct gate. `CheckpointZone` construction 0x3959b4 uses the generic Zone constructor. `OnCollisionBegins` 0x395f04 first requires contact-object `IsZonable` (virtual+36), resolves Character, then requires `IsPlayer` (virtual+40) and pointer equality with local player 0, and suppresses the same checkpoint key at Character+5224. Raw ARM at 0x396034–0x396044 proves the call passes arg3=false to `LevelCheckpointSave`; it stores the zone position as the checkpoint key but the current Character position (Character+352) as revive+5236. `Level::CheckpointSave` 0x3f04b4 separately requires LevelSavegame+236, Level lifecycle/state field+304 >33, a local Character and `!IsDead`; it records checkpoint key/revive position, calls `SG_SaveCheckpoint`, then `LevelSavegame::SaveCheckPoint` (0x463130). Thus a checkpoint can be saved during combat and the respawn point is the Character position at contact, not the zone center. The writer filter byte+40 is true by default for Character/Container/Door/Module/native-Trigger constructors, false for ObjectBase/Dummy/Waypoint; native Trigger constructors are 0x398f44/0x398fd4. Area `Zone`/`TriggerZone` is a different class: `ZoneCtor` 0x397c2c directly calls `GameObject` construction and does not set byte+40, so eligibility is not inferred from an area-zone name. `GameObject::InitPost` clears byte+40 when byte+348 is true. The authored `skip_checkpoint` property is registered in canonical `assembly-functions.asm` line 104672 (byte+348, default false); existing `game_object_initialization_owner_v1` projects it to checkpoint eligibility. The source rule is constructor-family default eligibility plus `!skip_checkpoint`; generic Zone and ObjectBase/Dummy/Waypoint remain ineligible absent an explicit write. Lever/AnimatedObject/TriggerObject inheritance still needs a separate constructor/property trace before inclusion. The portable capture requires this explicit actor/object eligibility provider and never assumes every object qualifies.\n- `Level::LoadCheckpoint` 0x3f0428 sets the Level loading flag, calls `LevelSavegame::LoadCheckPoint` 0x46259c if the same LevelSavegame exists, then `GameEventManager::ReInit` 0x47992c. It next gets local PlayerInfo and, when a Character is present, calls `Character::SG_LoadCheckpoint(...,16)` 0x3bc4bc then `Character::SG_Update(...,true)` 0x3bc480, finally clearing the loading flag. `LevelSavegame::LoadCheckPoint` switches the same cache to the current checkpoint filename, refreshes it, loads INFO then OBJS, then restores the ordinary LevelSavegame filename/cache.
- The OBJS player branch is now resolved rather than unknown. `LevelSavegame::__LoadObjects` 0x461e90 special-cases `PlayerCharacter_0` to the same local Character and dispatches its virtual load. `Character::Deserialize` 0x3a6210 reads GameObject state and Character state/position/rotation/dead/revive coordinates. For a Character that passes `IsPlayer` at vtable+40, it calls vtable+64 with true; the raw `_ZTV9Character` at 0x965f30 (vtable address point +8) maps that slot to `GameObject::SetVisible(bool)` 0x38b0f0. `Character::IsPlayer` 0x3a49f0 uses character type 1 or a `PlayerCharacter` name. That callback does not call PlayerSavegame::SG_Load. Non-player characters load their two serialized CharacterProperties records. Deserialization also removes buffs before loading the base/object data. The Character restore logic first restores serialized Character+5193 (dead bool), then handles saved unsigned CS state only through 17: mask `0x1005` (states 0,2,12) attempts `CanRespawn`/Limbus if not already there and sets dead true; mask `0x20002` (states 1,17) enters PreSpawn if needed while retaining the saved dead bool; otherwise saved-dead sets HP0/AI dead and attempts Limbus, while saved-alive initializes a missing physical object and sets Idle(0). Every branch clears the saved target. The source planner encodes these ordered operations; it uses current physical-body presence because this fact is not part of Character Serialize. CanRespawn short-circuits false when the instance byte or Character property11 gate denies respawn, while a missing group-permission value remains an explicit gap only when those gates permit the call. This checkpoint OBJS path does not reload player profile sections.
- The checkpoint OBJS writer's admission is also explicit. `LevelSavegame::__SaveObjects` 0x462d84 walks the ObjectManager's sorted object map and serializes each present object whose checkpoint-enabled byte at object+40 is nonzero. Offline, that is the complete object filter. Online, it additionally excludes remote player Characters and local player Characters with disabled byte+129 set. It writes the object's gametype, persistent name (normalizing player Characters to `PlayerCharacter_0`), room, and the full virtual Serialize payload. No class-specific dropped-item filter is visible in this writer: a loot/drop GameObject is included if the manager contains it and its checkpoint flag is enabled. The available export does not establish which dynamically created loot actors satisfy those two predicates. During load, the same initialization flag gates the whole reader; saved player names resolve to the same local Character, other names resolve by ObjectManager name/room, and a missing saved object is skipped after advancing over its payload. The load path neither creates missing saved objects nor deletes currently present objects omitted from the checkpoint. Thus unsaved/current objects can remain; exact consequences for dynamic drops remain unproven.
- INFO is the Level row, not an unidentified procedural seed. `__SaveLevelInfo` 0x4616b8 writes LevelSavegame field+40 (row28); `__LoadLevelInfo` 0x461820 reads that int into field+44 (loaded_row2c). The existing `level_validate_checkpoint_v115` compares loaded_row2c with the requested Level row, corroborating this mapping. Checkpoint load records the saved row but `Level::LoadCheckpoint` itself does not use it to admit/reject the restore. This evidence does not identify a saved RNG/procedural-generation stream.
- The later `Character::SG_LoadCheckpoint(16)` delegates to `PlayerSavegame::SG_LoadCheckpoint` 0x465450. When the checkpoint Savegame receiver exists, it selects the checkpoint player-save filename, calls `_cacheFile(NULL)`, `SG_Load(16)`, then restores the regular profile filename. `PlayerSavegame::SG_Load` 0x465430 runs `_Load(16)` and `_LoadVolatileQuestsLog(16)`. `_Load(16)` 0x464f4c initializes quest state and reads only QEST; it does not read LVLS, SKIL, FAES/CFEE, PROP, GEAR or FTVL. `_LoadVolatileQuestsLog` 0x468574 first gates on `flags & 0x14`, then on online mode; the offline local-death route therefore does not read the online volatile quest stream. The later `SG_Update(true)` delegates to `PlayerSavegame::SG_Update` 0x4636c4, which runs `SG_TryQuestSync` and `QuestSavegame::UpdateQuests(...,true)`.
- Checkpoint persistence effects are bounded by the serialized source records. `Level::CheckpointSave` 0x3f04b4 → `LevelSavegame::SaveCheckPoint` 0x463130 records the current zone and character revive position (`CheckpointZone::OnCollisionBegins` 0x395f04). The checkpoint Level save writes INFO and OBJS (`__SaveLevelInfo` 0x4616b8, `__SaveObjects` 0x462d84); load reads the corresponding sections (`__LoadLevelInfo` 0x461820, `__LoadObjects` 0x461e90). INFO contains the Level row integer (field+40 in the save owner, field+44 after load); it is not a procedural seed. OBJS contains named/type-tagged object payloads: `GameObject::Serialize` 0x38b9e4 persists base/spawn-probability state; `Character::Serialize` 0x3a65c4 persists character state, location/rotation, death state and revive coordinates; `Container::Serialize` 0x39f8e0 persists its open/state byte. On load, a matching existing object is deserialized; absent saved objects are skipped in the observed path. `GameEventManager::ReInit` 0x47992c and `GameEvent::ReInit` 0x479538 run after load and can refresh event/objective state. Therefore saved named characters and containers have source-supported restoration paths, and quest state has an explicit QEST restore. This audit does not prove that every enemy subtype, dynamically created drop, loot result, RNG stream/procedural seed, or unnamed object is restored; dynamic respawn consequences remain unknown.
- Checkpoint restore/provider contract for integration: `load_level_checkpoint` must use the same LevelSavegame cache and ObjectManager for checkpoint filename/cache refresh and INFO/OBJS restore. The OBJS provider must dispatch `PlayerCharacter_0` through the actual Character Deserialize path; that callback restores character/base object pose, death and revive-position fields and calls `SetVisible(true)`, but does not load player-save sections. Then the separate `load_character_qest_checkpoint` provider maps to `Character::SG_LoadCheckpoint(16)`/PlayerSavegame QEST-only restore, and `update_character_quests` maps to `Character::SG_Update(true)`. Never substitute a full GameSave/profile load: checkpoint flag16 does not reload LVLS, skills, faeries, properties, gear/inventory or fast travel, and OBJS player Deserialize calls SetVisible rather than SG_Load. `restore_revive_position` must use the Character revive coordinates saved by checkpoint and move attached objects as source does. `revive_to_source_vitals` maps to `Character::Revive(...,1)` and `_InitHpMp`, leaving resulting HP/MP source-derived. Buff clearing, Idle, minimum potions, and music each have separate providers and must preserve source order. Full F9/profile restoration is not equivalent to this checkpoint path.
- Separate `Application::GoToMainMenu` 0x32c1f4 quick-saves Level and local player, resets MenuManager, switches to Flash menu and removes players; it is not the Continue/revive callback.
- Online-only `_CheckGlobalDeaths` 0x375eb4 requires all connected players to be assigned and dead before `CMsgGlobalDeath`. `_HandleGlobalDeaths` 0x375af0 pushes fade/mutes FX, coordinates peers, host-loads checkpoint/restores host position, forces world update, waits 2000ms, then fades and calls `ReviveLocalPlayers(...,1)`. This is separate from offline local Continue.
- `Character::CanRespawn` 0x3a5248 and `GetRespawnDelay` 0x3a4bac derive Character/group respawn eligibility and delay from a flag/property11; they are not gates for the player local-death flow.

## Expected behavior, implementation and verification

Offline local death must preserve the Level/character/dead/phase gates. Continue performs only the single source action `parent.gotoAndPlay("Hide")`; its authored timeline later invokes the frame-88 revive callback. Duplicate clicks/callbacks must not replay effects. Save ownership and exact HP/MP remain with source providers. Online timer and global-death routes remain separate and cannot run offline checkpoint loading from the local timer branch. Exact source objects and geometry are now recorded, while assembled visual match remains open.

Implementation: `death_flow_v1.{hpp,cpp}` wraps existing `death_restart_v1`, separates the exact one-call Continue label jump from the frame-88 revive, guards duplicates, and preserves the second music callback. `death_screen_v1.{hpp,cpp}` exports immutable source object/layout/timeline metadata; `death_screen_renderer_v1.cpp` renders exported SWF shape739/496 geometry through the triangle API and delegates localized source text to the source font/text provider. New `death_screen_runtime_v1.{hpp,cpp}` exposes deterministic 30fps frame advancement, the authored release hit test, one-shot Hide jump, frame64 callback, and frame88 revive ordering without owning the host loop or renderer. `death_fade_from_black_v1.{hpp,cpp}` steps sprite743 at 30fps through its frame32 pop; `death_fade_from_black_renderer_v1.cpp` draws retained shape496 triangles with source transforms. New `death_checkpoint_load_v1.{hpp,cpp}` exposes the exact Level::LoadCheckpoint callback order, typed reached/failure phases, one-shot admission, and loading-flag cleanup after provider errors; it keeps reached world mutations and stops later callbacks instead of inventing transactional rollback. The runtime-focused suite covers opening stop/Continue, early Continue skipping the unvisited frame64 callback, frame88 effect order, online rejection, invalid hit, failure/duplicate behavior, checkpoint/no-LevelSavegame/no-local-Character branches, both checkpoint receiver and SG_Load(16) fallback, each provider failure prefix/flag cleanup, the full source743 alpha/pop sequence including duplicate and failed pop, Character CS-state branch outcomes, and checkpoint snapshot codec round-trip/checksum/identity/QEST/finite-transform rejection. Renderer and snapshot translation units compile independently with warnings as errors. Combined executable wiring, actual lethal-hit → rendered original screen → Continue → frame88 runtime, and isolated-save/world comparisons remain open integration gates.

Focused implementation tests pass via `run_death_flow_v1_tests.ps1`; existing `run_death_restart_v1_tests.ps1` also passes. Normal production wiring, frozen-executable runtime and rendered visual verification remain pending with the integration owner.
