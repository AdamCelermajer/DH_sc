## IDA / recovered logic

The IDA export `.local-inputs/ida-apk-export-2026-10-07/libraries/libDungeonHunter2.so` is APK v1.0.2, while videos are v1.0.3; version differences remain possible.

- `PlayerManager::Update` 0x378fb4 calls `_CheckLocalDeaths` 0x376100 and `_CheckGlobalDeaths` 0x375eb4. Local gate: current Level exists/type 38; local player has a Character; its virtual +52 dead predicate is true; manager phase +433 is positive. `_HandleLocalDeaths` is 0x375fe8.
- `_HandleLocalDeaths` offline: if `menu_FadeToBlackScreen` is not visible, push it once and mute FX. Online: use state +1809 and the local death timer/HUD; expiry hides the timer and calls `ReviveLocalPlayers(...,0)` without offline checkpoint reload.
- `NativeReviveAllPlayers` 0x43b1e4 requires current Level type 38. Online it sets manager +1816 and returns. Offline it pops `menu_FadeToBlackScreen`, pushes `menu_FadeFromBlackScreen`, then calls `ReviveLocalPlayers(...,0)`. The SWF registers it through MenuManager's native registration path.
- `NativeScreenIsBlack` 0x439fa4 does not inspect pixels; online it advances manager +1812 from 1 to 2. `NativePlayPreviousMusic` 0x43ad58 calls `RestartMusic(0)`.
- Offline `ReviveLocalPlayers` 0x37565c restores FX volume, calls `Level::LoadCheckpoint`, clears Character buffs, restores non-origin revive coordinates, calls `Character::Revive(...,1)`, sets Idle, ensures `CharacterDesign.MinimumPotionsOnDeath`, then stops current music and starts Level music with a 1000 ms fade. The SWF's later previous-music call is distinct and must remain distinct.
- `Character::Revive` 0x3a59ac initializes HP/MP via `_InitHpMp`, marks alive, initializes its physical object, floor-corrects position offline and updates skills.
- `Level::LoadCheckpoint` 0x3f0428 loads the current Level checkpoint, reinitializes GameEventManager, then invokes `Character::SG_LoadCheckpoint(...,16)` / `SG_Update(...,1)`. `PlayerSavegame::_Load` 0x464f4c shows bit16 loads only QEST; LVLS, SKIL, FAES/CFEE, PROP, GEAR and FTVL are not reloaded by this branch. Thus this restores checkpoint world/quest state, not the whole profile.
- Checkpoint persistence effects are bounded by the serialized source records. `Level::CheckpointSave` 0x3f04b4 → `LevelSavegame::SaveCheckPoint` 0x463130 records the current zone and character revive position (`CheckpointZone::OnCollisionBegins` 0x395f04). The checkpoint Level save writes INFO and OBJS (`__SaveLevelInfo` 0x4616b8, `__SaveObjects` 0x462d84); load reads the corresponding sections (`__LoadLevelInfo` 0x461820, `__LoadObjects` 0x461e90). INFO contains one integer whose semantic name is not established in this export. OBJS contains named/type-tagged object payloads: `GameObject::Serialize` 0x38b9e4 persists base/spawn-probability state; `Character::Serialize` 0x3a65c4 persists character state, location/rotation, death state and revive coordinates; `Container::Serialize` 0x39f8e0 persists its open/state byte. On load, a matching existing object is deserialized; absent saved objects are skipped in the observed path. `GameEventManager::ReInit` 0x47992c and `GameEvent::ReInit` 0x479538 run after load and can refresh event/objective state. Therefore saved named characters and containers have source-supported restoration paths, and quest state has an explicit QEST restore. This audit does not prove that every enemy subtype, dynamically created drop, loot result, RNG stream/procedural seed, or unnamed object is restored; the INFO integer meaning and dynamic respawn consequences remain unknown.
- Checkpoint restore/provider contract for integration: `load_level_checkpoint` must implement `Level::LoadCheckpoint` including the checkpoint Level OBJS/INFO reader, GameEventManager reinitialization, and player `SG_LoadCheckpoint(16)`/`SG_Update(1)` semantics. Flag16 is QEST-only. Do not map it to a full profile save/load: LVLS, skills, faeries, properties, gear/inventory and fast travel are not loaded by that flag. The local Character checkpoint record may additionally invoke its virtual save-load callback (`Character::Deserialize` 0x3a6210 → `Character::SG_Load` 0x3bc4d0, whose wrapper delegates to PlayerSavegame); the complete field-level behavior of that callback is not asserted here. `restore_revive_position` must use the Character revive coordinates saved by checkpoint and move attached objects as source does. `revive_to_source_vitals` maps to `Character::Revive(...,1)` and `_InitHpMp`, leaving resulting HP/MP source-derived. Buff clearing, Idle, minimum potions, and music each have separate providers and must preserve source order. Full F9/profile restoration is not equivalent to this checkpoint path.
- Separate `Application::GoToMainMenu` 0x32c1f4 quick-saves Level and local player, resets MenuManager, switches to Flash menu and removes players; it is not the Continue/revive callback.
- Online-only `_CheckGlobalDeaths` 0x375eb4 requires all connected players to be assigned and dead before `CMsgGlobalDeath`. `_HandleGlobalDeaths` 0x375af0 pushes fade/mutes FX, coordinates peers, host-loads checkpoint/restores host position, forces world update, waits 2000ms, then fades and calls `ReviveLocalPlayers(...,1)`. This is separate from offline local Continue.
- `Character::CanRespawn` 0x3a5248 and `GetRespawnDelay` 0x3a4bac derive Character/group respawn eligibility and delay from a flag/property11; they are not gates for the player local-death flow.

## Expected behavior, implementation and verification

Offline local death must preserve the Level/character/dead/phase gates. Continue performs only the single source action `parent.gotoAndPlay("Hide")`; its authored timeline later invokes the frame-88 revive callback. Duplicate clicks/callbacks must not replay effects. Save ownership and exact HP/MP remain with source providers. Online timer and global-death routes remain separate and cannot run offline checkpoint loading from the local timer branch. Exact source objects and geometry are now recorded, while assembled visual match remains open.

Implementation: `death_flow_v1.{hpp,cpp}` wraps existing `death_restart_v1`, separates the exact one-call Continue label jump from the frame-88 revive, guards duplicates, and preserves the second music callback. `death_screen_v1.{hpp,cpp}` exports immutable source object/layout/timeline metadata; `death_screen_renderer_v1.cpp` renders the exported SWF shape739/496 geometry through the current triangle API and delegates localized source text to the source font/text provider. Focused tests cover admission gates; `gotoAndPlay("Hide")`; duplicate Continue and callback; callback rejected before Continue; provider failure; online route exclusion; geometry/source-area checks; panel, quote, and fade keyframe alpha; and renderer compile. Existing restart tests cover checkpoint/revive effect ordering and failure prefixes. Production executable, assembled visual UI, actual lethal-hit → Continue → frame88 runtime, and isolated-save comparisons remain integration-owner gates.

Focused implementation tests pass via `run_death_flow_v1_tests.ps1`; existing `run_death_restart_v1_tests.ps1` also passes. Normal production wiring, frozen-executable runtime and rendered visual verification remain pending with the integration owner.
