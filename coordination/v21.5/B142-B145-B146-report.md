## B142: hero death cannot revive once the Bogwomp Chief has spawned

### Evidence

- Visual: the user's report (hero lying dead, no revive). Reproduced in the earlier B142 partial session on the shipped/merged build (`Death host failed ... Source PreSpawn owner is not ported (saved CS state 17)`, hero stays dead), also documented in B141 review section 5. I did not re-run that baseline myself.
- Logic (IDA, `libDungeonHunter2.so/pseudocode-all.c`): `Level::LoadCheckpoint` 0x3f0428 calls `LevelSavegame::LoadCheckPoint`, which restores each saved object by name through its virtual `Deserialize`. `Character::Deserialize` 0x3a6210 maps saved state 1 or 17 to `SM_SetPreSpawnState` if not already PreSpawn (mask 0x20002). `CSPreSpawn::OnFocus` 0x3c688c: PreSpawn pose, `SetPhysicalObject(null)`, collisions off. `Trigger::Serialize/Deserialize` 0x398978/0x39890c save and restore the activation count (+948). `Level::_LoadProcess` (line 179611) writes the level-start checkpoint itself, so the port's `level_start` checkpoint has an original counterpart.
- Expected: revive at the checkpoint with full HP; the Chief returns to PreSpawn (hidden, no body) and the consumed scene trigger is armed again, so entering the zone replays the intro. Repeat deaths keep working.
- Uncertainty: original footage of a death/revive does not exist in the available material. The behaviour is from IDA only.

### Cause in our code

`main.cpp` `deathApplyState`: the restore plan emits `set_pre_spawn_if_not_already` for a checkpoint actor saved in state 17 whose live state is different (here the spawned Chief, live state 3). The op had no owner and refused the whole restore. The trigger activation counts were also outside the checkpoint subset, so even a successful PreSpawn restore would leave the scene consumed.

### Change (`d1e4d230`)

- `original_actor_lifecycle.{hpp,cpp}`: `enter_restored_pre_spawn` runs only the PreSpawn Focus effects and registers the record at 17. It is limited to the authored Limbus/PreSpawn baseline (`pre_spawn_baseline_ids`). Other actors still refuse explicitly.
- `main.cpp`: the death restore queues baseline actors for `enter_restored_pre_spawn` after the Session rebind and population admission. Checkpoint capture persists the campaign lifecycle (trigger counts) as a native-trigger family object, and the restore reapplies it with `campaignHost.restore_lifecycle`. A checkpoint written before this build has no record and keeps the live counts (logged as `not recorded (older checkpoint)`).
- Tests: `original_actor_lifecycle_tests` extended (refused non-baseline actor, failed effect leaves no record, Focus effects without Blur, notification carries the previous state, duplicate refused, re-spawn works).

### Runtime verification (fixed build, `b142-63a0bdbf.exe`)

- `runs/b142-natC`: Continue, walk in, scene plays, the hero dies naturally (frame 968), Space at the death screen (frame 1771). Log: `Source restore SetPreSpawnState actor=..._prim_Monster_05_325 previousState=3`, `Death checkpoint trigger state restored`, `Death checkpoint restored ... actorsRestored=46`, `Death Character::Revive HP=165.098/165.098`.
- `runs/b142-walkin`: the same, then W held to walk back into the zone. The scene replays (`LizCaptain_Intro started` at frame 2134) and finishes (2251). The hero then dies a second time naturally (admitted at frame 3205). **Gap**: the second Space was pressed at about 50 s, before the black screen (frame 3332), so the second revive was not exercised.
- Not run: a baseline (shipped) death run on this machine. The failure signature is from the B142 partial session and B141 review.

### Remaining gaps (B142)

- Checkpoints written before this build carry no trigger record. A death revive then restores the Chief to PreSpawn and keeps the consumed scene (the B141 "present but inert" state until the next checkpoint contact rewrites the checkpoint). B145's repair covers the save-side case, not this checkpoint case.
- The Equipment tab after a revive can refuse to switch (`Runtime equipment bare-definition policy does not support this ...`), reported by the earlier B142 session as pre-existing and not in this change. Not verified here.
- Other lifecycle actors without a PreSpawn baseline (Idle `auto_spawn=0`, pool slots) still refuse with the explicit message.

## B146: cave -> swamp round trip does not restore the swamp world

### Evidence

- Runtime baseline (`runs/b146-rt`, B142 build): swamp, scene completes, E to cave, E back to swamp. Log: `Level world restore status=refused detail=Saved object roster differs from loaded level (saved 29 live 17)`. The consumed trigger did not replay. The world (killed mobs, chests) was not restored.
- Logic: `LevelSavegame::Load` restores the level's objects by name for a visited level. Our arrival restore ran before the lifecycle, containers and world-gate objects were bound, so the roster never matched.

### Cause in our code

`main.cpp` arrival block: the restore executes during `startup`, before the level is complete (`saved 29` vs `live 17`), so it is always refused.

### Change (`0bf3c98a`)

The arrival admits the world file (level URI, profile, procedural seed checks) and schedules the same frame-0 replay that the Continue path already uses (`options.loadFrame=transitionFrameBase`, `resumeLevelWorld=true`, `arrivalWorldRestore=true`). The hero stays at the entry SpawnPoint (`adopt_live_character_for_world_restore(..., !arrivalRestore)`). The restore is atomic: a refused restore logs `Level world restore status=refused` and leaves the freshly loaded level. Continue and F9 keep their behaviour. The lifecycle and container restores run only when the world was restored.

### Runtime verification (`runs/b146-fix`, `frozen/b146-a94dc645.exe`)

- `Level world restore status=scheduled ... objects=29 actors=46 frame=941`, then `Arrival world restore frame=941`, `Level world restored level=data/scene/001_swamp.mlx objects=29 actors=46`. No error or abort lines after it. The consumed trigger did not replay (one `LizCaptain_Intro started`).

### Remaining gaps (B146)

- **The restored Bogwomp Chief comes back hidden (PreSpawn, physical=0)** instead of Idle with its body. The saved world records it as physically absent after its scene, and the restore helper (B141 `restoreLifecyclePreSpawn`) treats an absent presence fact as PreSpawn. I checked the saved world with the read-only parser (`physical=0`, `targetable=0`, HP 260). The stale fact is not isolated: the spawn path emits no `init_physical` from Spawn(1) to PreSpawn(17), and the first transition save writes the fact before the post-scene body is published. A guard on the saved state (1/17 only) was tried and had no effect (the session state is already 17 at that point), so it was reverted. The visible result is the same as the refused baseline (the Chief stays hidden and inert), so this is not a regression, but it is a fidelity gap.
- Killed mobs, opened chests and loot after a round trip were not verified (no kill or chest opening in the runs). Only the world restore itself, the absence of the refusal, and the non-replay of the consumed trigger were.
- Only the swamp -> cave -> swamp route was run.

## B145: aborted Bogwomp Chief scene in the user's save (optional one-time repair)

### Evidence and admission rule

- B141 review section 4 gave the admission rule: a consumed trigger whose spawn target is still never-spawned, alive, on its anchor, with the trigger count at least 1. The original cannot write this state, because `Script_BlockSaveGame` (0x45c8c0) prevents `LevelSavegame::Save` until the scene's closing `Script_SaveGame`, which runs only after `Script_SpawnCharacter`.
- The partial B145 session derives the scene facts from the compiled bank (`OriginalCampaignRuntime::trigger_scene_facts`: blocked spawn targets and kill targets reached inside a `Script_BlockSaveGame` window). The decision also requires every kill target to be alive, and the repair is stamped (`campaign_repairs_v1`) so a save is repaired once. No level, scene, trigger or actor name is used.

### Runtime verification (`runs/b145-usersave-base` vs `runs/b145-usersave-fix`)

Input: a copy of the user's save (`.local-inputs/v21.4/b141/usersave/`: trigger count 1, captive alive, Chief unspawned at its authored spawn).

- Baseline (B146 build, Continue): `Lifecycle restored PreSpawn ..._prim_Monster_05_325`, no `LizCaptain_Intro started`. The Chief stays hidden and the scene never replays. This is the reported problem.
- Fixed (`b145-91309627.exe`, Continue): `[repair] B145.rearm_aborted_blocked_scene_v1 PORT REPAIR (not original behaviour): trigger=...BigLizIntro was consumed ... armed once more`; `LizCaptain_Intro started`; `Script kill complete victim=..._prim_Monster_08_329` (captive); `scripted clip finished: _prim_Monster_05_325 state=3 -> Idle`; `Lifecycle final ... state=3 physical=1`. The stamp `campaign_repairs_v1` is present in the saved world file.

### Change (`cae4c885`)

- `features/campaign_host/aborted_scene_repair.{hpp,cpp}` (new) with unit tests `aborted_scene_repair_tests.cpp`: admission verdicts (captain already fighting, killed, not on anchor, unresolved, captive dead or unresolved, provider failure), the stamp, idempotence, the not-consumed case, and the second pass as a no-op.
- `original_campaign_runtime`: `trigger_scene_facts`, `rearm_trigger`.
- `campaign_host`: `repair_aborted_scenes`, stamp component `campaign_repairs_v1` (absent while empty, so unaffected saves stay identical), load tolerant to an unreadable stamp.
- `original_actor_lifecycle`: `at_pre_spawn_anchor`.
- `main.cpp`: `repairAbortedScenes()` runs once after the Continue/F9 restore and the lifecycle PreSpawn restore (`if(restored)`).

### Remaining gaps (B145)

- The repair runs only on the Continue/F9 restore path (the user's route), not on the death checkpoint path. It is a port repair, not original behaviour, and is labelled as such in the log and the stamp.
- One save copy only. Other triggers with the same abort history are covered by the generic rule, but no other save was tested.
- Saves older than game-save v3 (no physical-presence fact) are not covered: the rule needs a known absent presence fact.
- The B146 hidden-Chief presence gap above also applies to any Chief restored from a transition save.
