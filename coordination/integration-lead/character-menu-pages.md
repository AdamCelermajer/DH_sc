# Character menu: Quest Log and Map page source audit

Status: read-only requirements audit. This report does not add either page or claim menu integration. Source SWF is `port/android-native/app/src/main/assets/original-cache/data/menus/dqcharmenu_droid.swf` (SHA-256 `43227075f407626b52eca4c345ac6f568023fcb39c269588201026c0fc6760e0`). Action offsets below refer to `port/engine-ui/reference/character-menu-flow-v1/authored-actions.txt`.

## Shared character-menu route

The source root is `root/sprite267`. `btnQuestLogTab.onRelease` at `0x0000ed38` sets `LastSelectedTab="Quests"`, invokes `CharacterMenuTabs.switchTab(1)`, calls `NativePopAllAbove(1)`, and pushes the exact page name `menu_QuestLogSheetNEW`; it also plays `MenuTab` and resets the other tab controls to `Idle`. `btnMapTab.onRelease` at `0x0000ee4f` sets `LastSelectedTab="Map"`, changes rollover input behavior, calls `switchTab(1)`, then uses the same pop-above/push-page transition for `menu_MapSheet` and sound. Both routes require preserving the current single `CharacterMenuTabs` owner and normal menu-stack semantics.

Source page art is distinct: Quest Log is `root/sprite599` (`menu_QuestLogSheetNEW`; authored matrix `[1,0,0,1,170,2126]`); Map is `root/sprite655` (`menu_MapSheet`; authored matrix `[1,0,0,1,0,0]`). Do not substitute the similarly named legacy QuestLog sheet or the HUD mini-map page.

## Quest Log (`root/sprite599`)

The ActionScript calls `NativeGetQuestIDsInRange` twice to populate `AllQuests.content.Assigned` and `.Completed`, with the categories `"Active"` and `"Closed"`; returned entries contain the native quest title, source quest ID and whether the entry is the current quest. The native implementation (DungeonHunter2 pseudocode `NativeGetQuestIDsInRange`, `0x00443b18`) resolves the category using the source `GetQuestFunctor`, gets the same live player `Character`, walks `Character::SG_GetNumQuests` / `SG_GetQuestByID` / `SG_GetNextQuest`, sorts by `Quest::GetTitle`, and returns `{QuestTitle, QuestID, IsCurrent}`. This is live quest authority and save state, not a list that the menu may fabricate.

Selecting a row calls `NativeGetQuestDetails` with the player selector and native quest index. `NativeGetQuestDetails` (`0x0044c444`) checks against the same Character's quest count and publishes `Title`, `PreDescription`, `ObjectiveDescription`, `PostDescription`, and `IsPrimary` from the source `Quest`; the SWF writes those values into its title and three HTML description fields and chooses `QuestPrio`/localized `MENU_MAIN_QUEST` versus `MENU_SIDE_QUEST`. The AS source also localizes `GAMEPLAYMENUS_QUEST_LOG`, journal/completed headings, hero/party log labels, and `GAMEPLAYMENUS_QUEST_MAKE_ACTIVE` through `NativeGetStringFromSymbol`. Its party log visibility is controlled by `NativeIsMultiplayerGame`.

The activate button is visible only for a selected Assigned row. Its click path calls `NativeSetCurrentQuest(playerIndex, selectedQuestID)`; native `NativeSetCurrentQuest` (`0x0043d3b4`) resolves that player's Character and calls `Character::SG_SetCurrentQuest(id,-1)`, which selects the source difficulty. Completed rows cannot activate. Correct output therefore depends on the canonical same-profile `CharacterMenuQuestsV51` and `PlayerSavegameV1` already initialized by the source load path, plus source difficulty, current/primary quest state and multiplayer/player selection providers. The quests handoff documents the required canonical graph and explicitly says the current menu bindings do not yet publish it. No fixture quest, duplicate save, inferred completion, or default current quest is acceptable.

For a real acceptance reference, require the exact SWF sheet's authored art/text/hit contours plus an original runtime capture of both Assigned and Completed lists, one selected quest showing all four native text fields and primary/side presentation, and the action result for activating an assigned quest reflected by the same saved current-quest state. Capture the multiplayer party/hero-log branch only with its real multiplayer provider. No original-video capture for this page is cited in the current fidelity audit; acquire/identify one before claiming pixel acceptance.

## Map (`root/sprite655`)

The source sheet's `onShow` uses actual localization keys: `GAMEPLAYMENUS_MAP_TITLE`, `MENU_SHOW_LEGEND`, `MENU_MAP_RESET_ZOOM`, `MENU_MAP_CHECKPOINT`, `MENU_MAP_ENTRANCE`, `MENU_MAP_EXIT`, `MENU_MAP_QUESTGIVER`, `MENU_MAP_MERCHANT`, `MENU_MAP_CHAR`, `MENU_MAP_PLAYER2/3/4`, `MENU_MAP_ENEMIES`, `MENU_MAP_OBJ`, `MENU_MAP_LEGEND`, and `GAMEPLAYMENUS_LEGEND_ARROW`. It sets the legend warning state using `NativeIsMultiplayerEnabled`. `btn_Legend` calls `NativeShowMinimapLegend(true)` and opens the authored popup; the deadzone closes it and calls `NativeShowMinimapLegend(false)`. `btn_ResetZoom` calls `NativeResetMapZoom()`.

Native owner is `MenuCharMenu_Map` (`0x00453ccc` / `0x00453e28`), constructed around exact `menu_MapSheet`; native registration routes the two controls to this owner (`NativeShowMinimapLegend` sets its visibility flag; `NativeResetMapZoom` calls `MenuCharMenu_Map::ResetZoom` / shared `ZoomHandler::ResetZoom`). On `Show` (`0x00455138`), the native owner registers `RenderMap`, reads live visited/unvisited `RoomZone`s and current Level room bounds, clears/rebuilds icon collections, then populates player, NPC, map-exit, room-exit and current-objective icons and the level name. It creates and targets the actual map camera from the local player's live Character and current Level; hide restores the Level camera/player target and destroys the map camera. `ShowObjectivesIcons` (`0x004548ac`) reads the same local Character's current quest, resolves that quest, and obtains objective marker positions from its actual objective owners. The `MenuMinimap`/`HUDMinimap` implementation is a separate HUD owner and must not be confused with this character-map page.

Map acceptance needs the same loaded Level, RoomZone visitation and room bounds, current local player/Character, source object/NPC/exit registries, live objective/quest marker positions, original map camera and ZoomHandler ownership, and real multiplayer-enabled state. Missing world/object/objective providers should fail/omit only where original source does, never be replaced with invented markers or coordinates. Require the original SWF page art and a runtime reference from a known source level with real visited/unvisited rooms, local player, map/objective markers, and legend open/close/reset-zoom interactions; record level/profile/network mode with the capture. The current fidelity evidence does not identify an original Map page capture, so pixel acceptance remains pending.

## Wiring boundary / next integration step

Expose a typed Character-menu Tab/Action route only for selecting the source pages and keep the exact menu stack, source hit zones, labels and source art in their respective providers. Quest data/actions need an adapter over the already-published canonical quest/save owner described above. Map should be an isolated source-page provider over existing actual Level/room/player/object/quest/camera owners; it is not a static art-only tab. Root owns `main.cpp`, CMake and core/assets/packages; this audit recommends no edits there. The original source confirms route and responsibilities, but current root graph is not sufficient to claim either page is live.
