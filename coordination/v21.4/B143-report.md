## 1. Investigation (original behaviour)

Visual evidence: there is no footage of quit/relaunch/Continue (B086 already recorded that the P1/P2 references never show it). The only supporting observation is the original main menu slot panel in the v1.0.3 Part 1 video (`MENUMETA-survey.md` B3, 1:04-1:08): the profile panel shows the location text ("The Boglands") and Start game then goes to LOADING. That is consistent with, but does not prove, "Continue loads the profile's level". Inference vs observation: everything below about the load rule is from IDA, not from footage.

Logic evidence (`libDungeonHunter2.so`, APK v1.0.2 pseudocode `pseudocode-all.c`):
- `MenuBase::FS_ContinueGame` 0x420e64 (line 208095): builds `PlayerSavegame(slot)` and calls `Application::LoadLevel(LevelList[row].file, entry point, slot, resume flag, ...)` where `row` is `PlayerSavegame` word `levels[m_difficultyLevel]` (index 20+diff), the entry point word is index 16+diff (`LEPT`) and the resume flag comes from word 23+diff. The level is therefore the one stored IN THE PROFILE, not a fixed level.
- Who writes those words: `Character::SG_SetLevelId` 0x3bb854 (words 20+diff) and `Character::SG_SetLevelEntryPoint` 0x3bb89c (16+diff). `Level::_LoadProcess` case 0x22 calls SG_SetLevelId on every level load (MENUMETA-survey B2), `Level::_LoadPlayer` 0x3f0018 calls SG_SetLevelEntryPoint at the entry SpawnPoint, `Level::SG_SavePlayer` 0x3efa54 stamps date + entry, `FS_StartGame` writes row 41 (swamp). Saves happen at: level transition (`NativeGoToZone` QuickSave + `SG_SaveAllPlayer`), checkpoints (`Level::CheckpointSave` = `SG_SaveCheckpoint` + `LevelSavegame::SaveCheckPoint`), and `Application::Quit` 0x323bc4 / GoToMainMenu (`Level::QuickSave` 0x3f059c then `SG_Save`), per B086.
- Profile vs level save: `LevelSavegame::Load` 0x46156c reads only the sections `INFO` and `OBJS`; `__LoadObjects` 0x461e90 deserializes the level's objects and the local player object `PlayerCharacter_0` through `Character::Serialize` 0x3a65c4 (state, positions, CharacterProperties, flags). The profile (inventory, items, skills, XP, points, potions, quest state) is the separate `PlayerSavegame`/`Character::SG_*` and "is not reloaded by [LevelSavegame::Load]" (B086 report, same reading). So: the profile owns the character, the per-level save owns that level's world and the hero's position/state.
- Uncertainty: whether the original restores the player's `CharacterProperties` (HP/MP) from `PlayerCharacter_0` at Continue is not established (Character::Serialize writes them behind a virtual predicate I did not resolve). Quit writes both at the same moment, so the user-visible difference only appears for a profile written after the level save (see section 6). The Windows port keeps its own B086 rule "a profile with HP<=0 projects to full HP" (player_profile_properties).

## 2. Our code and why cave progress was lost

- Level choice: `start_same_state` (menu Continue and Start both end there) only did `if(options.level.empty()) options.level="data/scene/001_swamp.mlx"`. `--level` comes from the package `startup.args`, so Continue ALWAYS loaded the swamp, ignoring the profile's `menu_metadata.level_row[difficulty]` (our SG_SetLevelId; stamped by `stampSaveMetadata` at transition/quit/F5) and the entry component (our LEPT).
- Character source: the Continue frame-0 restore (`restore_game_save`) does `character_state = snapshot.character`, i.e. the Character embedded in `character.world-<level>.gsave` replaces the profile that the menu loaded. The swamp world file is written at the swamp->cave transition, so it predates all cave progress.
- Write order: transition = `saveLevelWorld("transition")` (world file with the then-current character) -> entry component + metadata stamp -> `save_character`; quit/main-menu = `saveResumePoint`: world file and profile written from the same snapshot; F5 = `gameplay.save` + profile; checkpoint zone contact = world file + `.source-checkpoint-v1`.
- Reproduced on the real path with the merged EXE (`frozen/baseline-5E156174.exe`, = `.local-inputs/v21.4/root/build/dh-foundation.exe`, SHA256 5E156174...): case `cases/BASE-S1`. Stage 1: Continue, E to the cave, kills, `LeatherArmor01` + gold pickup (`gold=16->24`, `stacks 11->12`), potion `4->3`, skill `row=4 rank=1->2 points=1`, quit: `Resume point saved ... level=...witchcave`; `character.save` = xp 18, gold 24, 1 skill point, Hardiness 2, potions 3, levelRow 44, entry 0@cave. Stage 2 Continue: `Continue level world status=valid level=data/scene/001_swamp.mlx`, `Restored live checkpoint HP=153.184` (the stale embedded character; swamp world has xp 6, gold 16, 2 points, Hardiness 1, potions 4); the Inventory page shows Potions: 4 and 16 gold (`BASE-S1/s2-continue-f800.png`); the player is in the swamp.
- Two more defects found on the same path (not in the report that opened the bug), both reproduced:
  1. The GameSave character section does not serialize `CharacterState::components`, which hold the transition entry point (`dh2.transition.entry.v1`) AND the procedural level seed (`dh2.procgen.seed.v1`). Every `restore_game_save` (F9, Continue restore) therefore wiped them from the live profile. After F5/F9 in the cave the profile lost the cave seed; the next Continue generated a different cave layout under the saved world and aborted: `Foundation error: Live save authored-actor migration: Saved roster omits actor without source admission receipt` (`cases/FIX2-F5F9`, signature d7bb... vs 7730...).
  2. F9 reads the single global `gameplay.save`. In the cave without a previous F5 (or with another profile's file; the package gameplay.save is profile-slot-2's swamp state) it throws and terminates the process (`cases/BASE-F9`, exit=1, same error).

## 3. Implementation (minimal, reusable, no invented rules)

- `features/menu_metadata`: `resume_level_uri(profile, LevelList, uri)`: the Continue level is the profile's `levels[CurrentDifficulty]` row (FS_ContinueGame). Refuses (caller keeps its level) for unknown metadata, unset row, row outside the table.
- `main.cpp` `start_same_state`: Continue picks that level. Guard: the profile level is taken only when it can be started from the profile, i.e. the per-level world save exists or the profile recorded its entry point for that level; otherwise `--level` stays with a log line. `--level` stays the default for legacy profiles.
- `main.cpp` Continue startup check: when there is no usable level world (none, unreadable, other level/profile, or a procedural level whose seed is unknown), Continue is a plain LoadLevel at the entry the profile recorded for that level (existing arrival path, `Continue arrival at the recorded entry`); profiles without a record (every v21.3 swamp-only save) keep the launch placement.
- `game_save`: `adopt_live_character_for_world_restore`: a level-world snapshot restores the world (all other actors, objects, RNG, the hero's saved position); the Character and the hero record are the live ones that were built from the profile. Used by the Continue frame-0 restore and by the transition-arrival world restore (which now also refuses instead of throwing). F9/R checkpoint restores of `gameplay.save` are unchanged (a quick-load still rolls the character back, as before).
- `game_save`: `restore_game_save` keeps the live `components`, since the file format cannot carry them.
- `main.cpp` F9: `liveCheckpointAdmitted()` refuses (log `Restore refused`) a missing/unreadable checkpoint or one of another level or profile instead of aborting; the guard runs before any state is touched. Diagnostic: object-roster refusal now prints saved/live counts.

## 6. Remaining gaps / risks (honest)

1. Pre-existing and not fixed: the world restore at a TRANSITION ARRIVAL into an already visited level is always refused (`Saved object roster differs from loaded level (saved 29 live 17)`): the restore runs before the campaign host has created its objects. Consequence: killed monsters/opened chests of a level are not kept when returning to it by E (the character is). It also means the arrival use of `adopt_live_character_for_world_restore` is covered only by the unit test, not by a runtime case. Continue frame-0 restores are not affected.
2. Pre-existing, observed: skill spending is not written to the profile until a save point, and a quit save that keeps being rejected for 90 frames (hero in an action, `Resume point retry`) is dropped, losing everything since the last save point (`FINAL-S2`). Not changed.
3. A Continue whose level world is valid but does not match the regenerated level (the world file does not record the procedural seed it was made with, so a profile that holds a different non-zero seed is not detectable) still aborts at the frame-0 restore as before. A profile with no seed at all is handled (`seed_unknown`). I did not add a general fallback.
4. Whether the original restores the player's HP/MP from the level save (uncertainty above) is not established; the port now takes HP from the profile on Continue. They are equal after a normal quit.
5. Behaviour change to be aware of: with a profile that records another level, `--level` no longer wins on menu Continue (tests that relied on `--level` with a profile stamped elsewhere must use a profile that matches). `gameplay.save` remains one global file (not per profile/level); F9 now refuses instead of crashing but a same-level/same-profile file from a different session is still restored.
6. Not run: full CTest, slot 3, a cave save followed by a THIRD-level target (no other reachable level in this package), original-video comparison (none exists).
