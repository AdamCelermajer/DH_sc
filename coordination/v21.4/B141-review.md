## 1. Root cause: CONFIRMED

Code:
- `main.cpp` (base): lifecycle records are created once in the level-start loop (`actorLifecycle.add`, ~line 3617). Both restore sites (Continue/F9 at ~7162 and death checkpoint at ~6010) called `actorLifecycle.clear()` and never rebuilt, because records hold `ActorState*` into the replaced world. `OriginalCampaignWorldAdapter` kind 30 -> `lifecycle_->spawn(id)` -> `Unknown original lifecycle actor`.
- `CampaignHost::frame` failure path (`campaign_host.cpp` ~830) calls `abort_cutscene`, which restored HUD/SKIP/locks/save-block but never the camera target (`SetCameraTarget(captain)` #2 stays latched; the authored closing `SetCameraTarget("")` #20 never runs) and left `scripted_` marks.
- Original: `Character::Deserialize` 0x3a6210 (pseudocode line 122392 ff.): saved state mask `0x1005` (0, 2, 12) -> Limbus; mask `0x20002` (1, 17) -> `SM_SetPreSpawnState` if not already; dead bit -> Limbus; else `InitPhysicalObject` if no body, Idle. `Character::Serialize` 0x3a65c4 writes `SM_GetState`. So an unspawned captain (or one saved mid-Spawn) comes back in PreSpawn and a later `Script_SpawnCharacter` (0x45f400) works on it. The original has no per-actor lifecycle registry that a restore could lose.

## 2. Fix generality and safety: PASS

- Not keyed to names. `restoreLifecyclePreSpawn` iterates `actorLifecycle.pre_spawn_baseline_ids()`, i.e. exactly the actors that `add()` registered as preset PreSpawn/Limbus from authored facts.
- Registers only when ALL hold: no record yet (`actorLifecycle.status(id)` empty, so no double registration; `restore_pre_spawn` also refuses an existing record), actor `alive()`, not `source_limbus`, `source_physical_present` known and false, actor still in the population. Dead, Limbus, despawned, removed and Idle/physical actors are skipped. Evidence: in the user's damaged save copy the dead `_prim_Monster_LizManIntro1/2` were NOT re-registered (3 records restored vs 9 in a clean pre-trigger save); in `contF9` the second restore re-registered 9 again without error.
- No transition effect is replayed (`restore_pre_spawn` makes no `invoke`; unit test asserts empty effect log). The later Spawn transition runs the identical code as on a fresh level (visible in the fixed scene). The state-17 session publication is only made when the live state is not already 17, so it does not set `lifecycleActivity` in the normal case (F5 after Continue still saves; owner `f5-fix` identical to shipped).
- No guard weakened: `CampaignCameraAdapter`, lifecycle `failed` and unknown-actor errors are unchanged; an actor outside the baseline still fails explicitly.
- Both restore sites now call `detach_for_restore()` (baseline kept) and re-register after rebind (Continue/F9) or after captured population admission (death). `clear()` stays the full reset and is still used by the R-reload and level change paths; both rebuild baseline through `add()`.
- B126/B127/B128/B131: the fix touches no death/despawn/admission/physical-body logic, only adds a record for actors already restored as PreSpawn (the exact Deserialize mapping B131 documents). B131 restore planning (`set_pre_spawn_if_not_already` error) is untouched; see section 5 for the interplay. `despawnHome` capture and permission provider consult `actorLifecycle.status(id)`, so a re-registered PreSpawn actor behaves like a fresh-level PreSpawn actor (combat permission false until Idle).
- Abort release (`abort_cutscene`: `scripted_.clear()` + zero-duration `seed_target(local player)`): matches the End contract (`Script_MarkCharacterAsScripted(false)` + authored `SetCameraTarget("")`). Correct for every abort cause that reaches `abort_cutscene` (failed command, failed SKIP fast-forward, camera-clip failure): clip and held clips are already cleared there, `seed_target` with duration 0 needs no provider and cannot fail, and it is a no-op when the target is already the player. The Begin phase does not release the camera (unit test). It is a port policy, not original behaviour (the original has no abort); owner states this honestly.
  Residual (pre-existing, not a regression): an abort mid-scene leaves scripted actor poses held (`held_clip_actors_` cleared "pose stays as the clip left it"), so a captain/captive mid-clip would stay frozen. I did not find a reachable abort after the fix to demonstrate it (owner's `fix-d-play` aborts at End only because of the HP test fixture).

## 3. Residual gaps in the fix (caveats, not blockers)

1. Saves older than game-save version 3 carry no `source_physical_present` fact; the baseline check requires a known `false`, and `restoreLifecyclePreSpawn` runs before `rebuildNativeBodies` publishes the fact, so such a save would still abort (now with camera released). The user's world save is v6. Cheap follow-up: treat "unknown presence" for a baseline actor whose saved state is PreSpawn as absent, or run the registration after `rebuildNativeBodies`.
2. Only preset PreSpawn/Limbus actors are re-registered. Idle `auto_spawn=0` actors, pool slots and actors despawned to Limbus still have no record after a restore (owner's gap list, agreed). Original `Script_SpawnCharacter` works on any Character, so a later scene spawning such an actor would still abort.
3. The death-checkpoint restore does not call `campaignHost.restore_lifecycle`, so trigger counts persist across a death revive, whereas the original restores `Trigger` objects from the checkpoint (`Trigger::Deserialize` 0x39890c reads count +948/timer +952). Latent: after a revive the world is back at checkpoint (Chief PreSpawn, captive alive) but the consumed trigger would not replay the scene. Currently masked by section 5 because the revive itself fails once the Chief has spawned; it will appear when section 5 is fixed.
4. A re-registered Chief combat permission after Continue was not separately exercised (hero attacking the unspawned captain after Continue). Not needed for the reported scenario.

## 4. Damaged saves (answer to the user's question)

### (a) Exact state of the user's save (copy `.local-inputs/v21.4/b141/usersave/character.world-001_swamp.gsave`, game-save v6, read-only parse with my `tools/ps.py`)
- Trigger activation counts (`campaign_lifecycle_v1`): `corner_ruin_ws_00.mgp::_prim_TriggerZone_BigLizIntro` = **1** (consumed) and `_prim_Zone_EnterLoc_south` = 1; hero stored inside the BigLizIntro zone at (-6295.4, 9515.8, 255).
- Captive `_prim_Monster_08_329` (id 6946165196097391975): **alive**, HP 47.5/47.5, dead=0, physical=1, targetable=1, at its authored post (-6549.6, 11309.5, 378.9).
- Captain `_prim_Monster_05_325` (id 15701623593687927299): HP 260/260, dead=0, limbus=0, **physical=0, targetable=0**, at its authored spawn (-6690.8, 11451.3, 379.1).
- Therefore: this is **"aborted", not "done"**. A done scene (End contract `SaveGame` runs after SpawnCharacter and after KillActor) leaves the captive dead (dead bit, Deserialize Limbus branch) and the captain Idle with a physical body at its fought position, or dead if the player killed it. Captain unspawned + captive alive + trigger consumed is a signature no completed scene writes.
- What the player sees in that state (confirmed visually: shipped `fight_S`, user screenshot): the brown beast and the green lizard stand in the chamber, inert and un-targetable; the scene never replays.

### (b) How the original persists this (IDA pseudocode `.local-inputs/ida-apk-export-2026-10-07/libraries/libDungeonHunter2.so/pseudocode-all.c`)
- `LevelSavegame::__SaveObjects` (line 250012) writes every savable `GameObject` by name through its virtual `Serialize` (+16); `__LoadObjects` (249568) resolves the name with `ObjectManager::GetObjectByName` and calls `Deserialize` (+20). Triggers and Characters are both such objects.
- `Trigger::Serialize` 0x398978 writes the timer (+952) and the activation count (+948); `Trigger::Deserialize` 0x39890c restores both. `Trigger::Activate` increments the count; `Trigger::CanActivate` returns false once the count reaches the authored max (the port mirrors this as `triggercount`, default 1, counted at entry). The count is consumed at activation, before the scene runs.
- `Character::Serialize`/`Deserialize` 0x3a65c4/0x3a6210: per-actor state, HP, positions, dead bit (see section 1). No script-progress state is saved anywhere: a script is never resumed.
- Mid-scene saves do not exist: the scene's Begin runs `Script_BlockSaveGame` 0x45c8c0 -> `Level::SG_BlockLevel(1)` (`LevelSavegame` byte +57) and `Character::SG_Block(1)`; `LevelSavegame::Save` (pseudocode line 249195) returns without saving while +57 is set, and `Level::QuickSave` (used by quit/`Level::Unload`) goes through it. The End contract's `Script_SaveGame` 0x45c994 unblocks and calls `Level::QuickSave`. `LevelSavegame::SaveCheckPoint` (250126) calls `Savegame::saveAll` directly without the block byte; when a checkpoint can be written mid-scene is not established here (uncertainty).
- Reload at each stage (original): before the trigger: count 0, captain PreSpawn, captive Idle: scene plays on entry. Mid-scene or quit mid-scene: no new save is written, the previous save (count 0) is what loads: scene plays again. After the scene: count 1 (never replays), captive dead/Limbus, captain Idle where it stood and fights. After the Chief is killed: captain dead bit -> Limbus (respawn only if `CanRespawn`, outside this review); the captain is then absent and the scene stays consumed. So an absent Chief in the original means dead (or a never-triggered scene before entry), never "present but inert".
- The original has no abort path; the damaged state is a port-only artefact.
- Unverified: the meaning of the `Level+243` early-return in `Character::Deserialize` for monsters (probably a multiplayer/client mode), not relied on.

### (c) Recommendation for v21.4 (no new rule invented; not implemented)
Evidence from my runs on copies of the user's save:
- `dmg_F` (damaged save, fixed EXE, Continue): no abort, camera and HUD normal, scene does not replay, captain stays inert (3 PreSpawn records restored; the dead LizManIntro actors are not resurrected). The fix prevents any new damage from this cause but cannot heal old saves.
- `dmgfix_F` / `dmgfix_S`: a copy where only the BigLizIntro count and "inside" entry were removed from the `campaign_lifecycle_v1` component (checksum recomputed, tool `tools/rearm.py`): the **fixed EXE plays the full scene** (captain strikes captive, camera back on hero, HUD) while the **shipped EXE aborts again**. So re-arming is mechanically safe on the fixed build.

Recommended repair (offered to root, to be built only if approved): a one-time, logged load migration that re-arms a consumed trigger (count back to 0, drop its "inside" edge) only when BOTH hold: (1) the trigger's script SpawnCharacter target (derivable from the compiled script, not a name list) is still the never-spawned state, i.e. alive, full HP, physical=0, not Limbus, at its authored anchor, and (2) the trigger count is >= 1. Reasoning: the original cannot persist (count>=1 with that actor still PreSpawn) because the block byte prevents mid-scene saves and the End save runs after the spawn, so this combination proves an aborted run, not a finished scene; the captive's state is not needed as a discriminator (a captive killed earlier by the player would not change the scene). If the captain is dead, Idle, or has a physical body, do nothing (scene done or fought). Uncertainties to state with it: it is a port repair, not original behaviour; the original `CanRespawn`/Limbus handling of a killed Chief is not exercised; saves older than v3 lack the presence fact (section 3.1); other triggers with the same abort history are not covered unless the rule is applied generically across triggers, which would need its own review. If root prefers no repair, the alternative is to leave such saves as-is and note in release notes that already-damaged saves keep the consumed scene (the player can still continue; the Chief stays inert).

Answer in one sentence for the user: the Chief is not absent because the scene was "done"; in the damaged save the scene was aborted (captain never spawned, captive still alive, trigger consumed), and the original would only show an absent Chief if it had been killed, so the scene should be allowed to play once more, which v21.4 does not yet do for existing saves without the optional repair above.

## 5. New finding (pre-existing, not caused by the patch): death revive fails after the Chief has spawned

Runs `deathafter_S` (shipped, no restore) and `deathafter_F`, `chiefdeath_F` (fixed, Chief fight in progress, real Space keys on the death screen): scene completes, hero then dies, `Death Continue (Space)` is accepted, then `Death host failed frame=...: Source PreSpawn owner is not ported (saved CS state 17)`. The hero stays dead on the field (sheet `deathafter_F/sheet.png`). Cause: the death checkpoint (level start) holds the Chief at saved state 17, the live Chief is now Spawn/Idle, and `deathApplyState` returns that error for `Op::set_pre_spawn_if_not_already` (`main.cpp` ~5967). It occurs identically on the shipped build without any restore, so it predates B141; before the fix a restored session never spawned the Chief and so never hit it. B141's lifecycle owner now exists and could execute the PreSpawn transition, but wiring it into the death plan is a separate B131-family change plus the trigger-count restore (3.3). Recommend a new bug entry, a named owner, and root deciding whether it gates the preview, since a Chief fight followed by death is a mainline path.
