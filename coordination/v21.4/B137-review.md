## Verdict: ACCEPT WITH CAVEATS

No change to the patch is required. The fix is correct, general for the arrival session, introduces no guard weakening and works in every real-input case I ran. One adjacent defect that the fix makes reachable (Continue restores a stale swamp-level snapshot over the newer profile) must be tracked as its own bug before anyone claims "progress made in the cave is saved" (caveat 1).

## (1) Root cause: CONFIRMED (code and logs)

Code (worktree `port/windows-foundation/main.cpp`, base 45a0c602): `frontendStarted` is a per-iteration local of the session loop (line 903), false for every non-frontend iteration. Every profile-bound branch keys on it: `equipmentStateInitialized=frontendStarted` (1399), `options.combat.selectedPlayerProfile=frontendStarted?&state:nullptr` (2109), level_raw from `state` (1828, 2112, 6823, 6839), the "Selected profile source projection" block (2120), per-instance equipment binding (2782), and the diagnostic bootstrap `if(!frontendStarted){...}` (2793-2830) which re-creates the starter items from `options.combat.equippedItemIds` and pushes the generated instance ids into the shared `CharacterState` next to the saved ones (`starter-item-N` from creation, `runtime_creation_persistence_v1.cpp:429`). The old arrival block loaded the profile but left `frontendStarted=false`.

Independent reproduction with the owner's pre-fix aid build `aid-0AB6B068.exe` (case `R23-prefix-aid`, real E): after "Transition confirmed" the log shows `Direct player source points ... known=1`, then `Equipment binding diagnostic: Shared CharacterState duplicates a source equipment slot`, then `Level start checkpoint status=not_saved result=5 detail=duplicate equipment slot: slot-0` repeated every frame. The same scenario on the final EXE has none of these lines. The owner's logs (`t4-equip-cave`, `t12-loot-potion-legacy`) show the identical sequence. The claim is supported.

## (4) Saved profile after a transition: file is sound; Continue discards it (CAVEAT 1)

- The profile written by the arrival sessions is well-formed: after loot/skills/round trips the `character.save` still has exactly the original 4 equipment rows and one instance each of `starter-item-0..4` (no duplicates), the new item appears once as `world-drop-1` (`R5`, `R10`, `R11-quit`, `R21-multihop`, string census compared with the original). The world-item adapter already de-duplicates ids with a suffix (`runtime_world_item_adapter_v1.cpp:405-415`).
- Reloading that exact profile by menu Continue works and shows the right state when the stale level world is absent: `R14` (R11 quit-save in the cave) shows Battle Hardened rank 2, 1 point left; `R15` (R10) loads, potions 2, new gear in bag. So no corruption.
- **However** the packaged Continue (and the package already ships `character.world-001_swamp.gsave`) restores the swamp level-world snapshot including its embedded character (`Continue restore frame=0 ... Restored live checkpoint ... HP=153.184`). That snapshot was written at the swamp->cave transition, i.e. before any cave progress. Result in `R12-continue-after-cave-quit`: the profile on disk had rank 2 / 1 point and HP 169.195, but after Continue the Skills page shows rank 1 / 2 points and HP 153.184: loot, potions, skill points and XP gained in the cave are discarded on the next Continue, and the next save would overwrite the good profile. This is the pre-existing "Continue always starts the swamp" behaviour (the owner noted the level part, report section 6) combined with Continue trusting an older snapshot over the profile. It is not caused by this patch and the arrival session itself is correct, but before the fix the cave never saved at all so it was invisible. Recommended: register a new bug (Continue must start the level stamped in the profile, or at minimum must not restore the character from a level snapshot that is older than the profile) with its own reviewer; do not describe B137 as "cave progress persists" until then.
