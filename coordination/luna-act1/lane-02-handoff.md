# Lane 02 handoff — application startup and main-menu flow

## Change delivered

In `native_menu_application_event_v120.inc`, added a scoped guard for `MenuManager`'s current-event field. Once the handler publishes the typed event identity, every return path now clears that field, including missing/failed typed payloads and downstream SWF input errors. Successful paths still return the source `event_consumed` value; the out-of-range or rejected multitouch path still reports consumed. The thread-local synchronous `SourceMenuConsumptionV121` loan remains nested inside the guard and unwinds first.

## Existing flow and reference evidence

The assigned startup/menu files already contain the retained GSInit stage owner, genuine stage 12 `MenuManager::Init` loop with the original 49 ms budget, stage 13 clock reset, stage 14 initial menu-state selection, MenuManager.Init phases 0–26, real LoadMainMenu resource/singleton/PostLoad path, Hide dispatch, and typed EventManager subscriptions for types 5, 4, and 7. The existing LoadMainMenu and selected Hide bodies remain dependent on current shared menu, preview, and renderer owners. No new owner or stub was introduced. `native_app.cpp`, input producer wiring, `model_renderer.cpp`, Java/JNI, CMake, build, and runtime validation remain with the coordinator as assigned.

### Concrete root proposals / unresolved points

1. GSInit stage 14 currently selects `menu_language` versus `menu_splash` from `OwnedHudSettingsV1::new_settings()`. IDA `GSInit::Update` at `0x3850c8` instead compares `dword_99F7F8` and `dword_99F7FC`; on its unequal branch it calls `Console::DBG_TryStartingLevel` before selecting `menu_splash`, and the equal branch consults SavegameManager byte `+55`. These operands are not proven equivalent to `new_settings()`. Expose the actual source branch inputs/console result through their existing owners, or leave this branch explicitly unresolved; do not infer it from settings. The same stage's GameCenter/orientation/internet/DRM tail needs only the platform branches selected by the intended offline build, with any excluded positive branches called out.
2. Keep the existing fail-closed phase-4 HUD gate as lane 06 repairs it. After that, the next broad sweep should capture the first unreached source operation by phase, especially singleton constructors and PostLoad/Hide; no source-host target currently runs those together.
3. Do not interpret the `startup-stage-v41` host report as GSInit coverage: its receipt covers telemetry-span parsing/accounting, not process startup. There is no existing host harness that executes `SourceGSInitProcessOwnersV100` plus native Init0–26, authored MainMenu Show/Hide, and Play on the real Android provider composition. Available host checks are component-level: `menu_manager_lifecycle_v58_audit` covers MenuManager unload/update; `run_menu_stack_v1_host.py` replays the MenuStack kernel and expects a prebuilt binary/gold fixture (on Windows its runner dispatches through WSL); SWF session/input and authored-menu lifecycle tests cover their own kernels. None initializes the App/Front/menu providers or drives this first-boot sequence. The startup telemetry target is likewise not a substitute. A useful source-host addition would need to factor the retained GSInit/MenuManager phase driver behind the current provider interfaces and inject real cache/SWF/menu kernels; a fake `World`/`Level` would be the wrong seam.
