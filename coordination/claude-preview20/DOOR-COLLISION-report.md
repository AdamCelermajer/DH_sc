# CORE P17 door collision — v20

Owner: `/root/v20_door_collision`; reviewer: `/root/v20_evidence_review`; integration owner: `/root/v20_integration`.

## Investigation and expected behavior

**Visual evidence (direct observation).** Reference is the supplied Dungeon Hunter 2 v1.0.3 Part 1 video at 640x360. Extracted original frames at 7:59 (`.local-inputs/v20/door-evidence/t479.png`), 8:01 (`t481.png`), and 8:03 (`t483.png`), plus 2-second contact sheets spanning 7:57–8:07 (`adjacent.png`) and 8:09–8:19 (`adjacent2.png`). The hero fights the Bogwomp Chief by a fixed stone arch; the frames show the boss taking hits and then disappearing with XP text. The camera shifts and the hero continues in the area. The arch does not visibly animate or open in these frames, and no traversal across its threshold is shown. This sequence confirms a static doorway in the environment only; it does not prove a door collision rule or an opening transition. Those are not inferred from the footage.

**Logic evidence (IDA and recovered owners).** In `.local-inputs/ida-apk-export-2026-10-07/libraries/libDungeonHunter2.so/pseudocode-all.c`:

- `Door::InitPost` (`003e7da8`, around lines 168276–168340) gates initialization on `CheckSpawnProbability < probability`, resolves the `Arrays::Doors` row and visual, calls `Zone::InitPost` and `MeetCondition`, registers animation callbacks, then calls `VisualObject::ApplyMeshBox`. If source byte `this+933` (`door_collision`) is true, it constructs a physical body with `(world,this,1,0,0,0,0,2,0xffff,1)` and assigns it via `GameObject::SetPhysicalObject(..., false)`.
- `Door::DeclareProperties` (`003e8990`, pseudocode near 168748–168794) exposes `opened` and `door_collision`; `Door` construction (`003e8274`) defaults `door_collision` to true.
- `PhysicalObject` polygon construction (`0046f2f0`, polygon branch) uses the same owner's absolute AABB XY extents and position, scales by 0.01, and builds a static rectangular body with category 2 and mask `0xffff`. `MP_NoCollisions` changes its group to -666. The shape uses the source `ApplyMeshBox` output; a render-bounds substitute is not justified.
- `Door::Open` (`003e786c`) admits only state 0 and `!busy`; `Door::Close` (`003e763c`) admits only state 1 and `!busy`. With skip or no visual they immediately call `Opened`/`Closed`; otherwise they enter state 3/2 and play the authored clip. The current physical filter is retained during the transition.
- `Door::__EventCallback` (`003e8450`) calls `Opened` on marker `opened` and `Closed` on marker `closed`; `Door::__Callback` (`003e8568`) completes the transition at clip end if no marker applied the end state. `Door::Opened` (`003e7788`) disables the body filter and clears floor-dead-end bit 1; `Door::Closed` (`003e7598`) enables the filter and sets that bit. `Door::InitFinal` (`003e7c1c`) applies the authored initial open/closed state after its spawn and condition gates. `PFWorld::FlagFloorAsDeadEnd` (`005252ec`) mutates `PFFloor+32` bit 1. `PFObject::CanPathOn` (`00524230`) reads `PFFloor+36`, so that flag alone does not establish blocking in the current Windows motion path.
- Existing recovered equivalents are `CanonicalDoorV27::init_post/source_transition_v91` and `CanonicalDecorPhysicalConnectionV49::create_door_physical` → `CanonicalPodDecorBodyV49::construct_door/assign`; filter mutation is reusable via `native_physical_filter_v1`. `construct_door` consumes the post-`ApplyMeshBox` absolute AABB and position, constructs a native static rectangle, and preserves assignment/lifetime order. The Windows `DoorRuntimeV1` currently has no consumer for these bindings; its `collision_closed()` is only a state accessor and incorrectly treats closing from open as blocked before the source callback.

**Expected behavior.** Each present Door with `door_collision=true` has one body made from the source visual's post-`ApplyMeshBox` absolute AABB and authored placement. A closed door blocks colliding actors. Open/close commands obey state and busy admission; the filter stays in its prior state while an animation plays, then disables/enables at the authored marker or clip end. Skip/missing visual applies the end state immediately. An absent door retires its body; restoring a state reconciles the filter without replaying animation or sound. `door_collision=false` creates no body. Movement clips a swept actor circle against the same door AABB with source group/mask admission, continuous crossing prevention, and tangent sliding; it receives the actor's source radius and MoveActor ignore-collision policy so all actor routes can use the same gate.

**Uncertainties.** The sampled video does not show this arch opening or a closed-door crossing. The exact source visual/door data identity at this arch has not been resolved from the video alone. Source `ApplyMeshBox` delegates `CalcMeshBox`; exact union behavior can depend on the model's `_colbox_` marker or static/skinned provider branch and the bind-time pose. A model that cannot produce the source AABB remains an explicit gap, never a guessed render extent. The staged `dummy_door.bdae` has no visible scene instances and the current `CharacterVisual` loader rejects it; the evidence does not yet establish whether it is used by a collision-enabled `Arrays::Doors` row or what bounds the source owner has in that case. Source collision behavior for `door_collision=0` declarations is clear from the property gate, but those map-specific declarations do not establish the behavior of all level doors.

## Implementation, isolated tests, and integrated verification

Implemented in the feature owner: source `door_collision` parsing (default true), a latched physical-filter value, and stable-ID physical binding snapshots. The filter value changes only when the runtime reaches its source end-state path; opening/closing clips retain the prior value. `source_door_apply_mesh_box_v1` borrows the same loaded DoorRuntime `CharacterVisual` scene and the same configured BRES asset. It runs the verified first `_colbox_` group/mesh path through `dh2_decor_scene` and the exact two-endpoint/recenter kernel, or uses the existing static/skinned `CalcMeshBox` provider path when no marker exists; it then publishes `dh2_decor_body_config`'s padded absolute bounds. `DoorRuntimeV1::adopt` captures this box before selecting the idle clip and exposes absolute XY bounds plus `source_bounds_valid` in each physical binding. It never reads `indexed_bounds()`.

Added `door_collision_v1` to reconcile create/retire/filter changes idempotently and to sweep an actor circle against source door AABBs, project remaining movement onto contact tangents, and retain rounded corner contacts. Source group/mask admission, actor collision disable, and MoveActor ignore-collision behavior are passed through. Missing active AABBs, duplicate IDs, nonfinite geometry and invalid actor inputs fail explicitly. Source slop is retained as a 0.5-game-unit contact allowance (the physical solver's 0.005 m tolerance).

Isolated tests were built with `p14_build.ps1 -Name v20doors -Jobs 4` after a private temporary CMake registration (the worktree's `CMakeLists.txt` was restored and that temporary hunk is not committed). `door_collision_geometry_v1_tests.exe` ran against `.local-inputs/v20/asset-stage/assets`: all seven shipped door/gate BDAE visuals passed finite, nonzero, translated/rotated source-box checks. It exercised marker and no-marker paths; `go_swamp_door_ruins.bdae` was tested at the authored `_prim_SwampDoor` position, and `go_swamp_door_ruins_fire.bdae` at `_prim_QueenDoor_01`'s authored -90-degree rotation/position. Both output game-unit centers matched the authored owner position. Their final XY extents were 230.65×1328.22 and 1724.63×415.804 game units respectively (including source ApplyMeshBox padding). `door_collision_v1_tests.exe` passed create/retire/filter reconciliation, duplicate/invalid IDs, large-step crossing, diagonal slide and corner near-miss, contact/away/tangent, multiple doors, open filter, collision-disabled actor, source mask/group, `door_collision=false`, and absent-door branches.
