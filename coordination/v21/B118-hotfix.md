# B118: Continue crashes while retiring restored dead summons

Implementation: fresh `/root/b118_continue_crash`; reviewer: fresh `/root/b118_continue_review`; root owns integration and release. Accepted v21.1 and the user's source seed are read-only; each run uses a private copy.

## Investigation before implementation

- **Visual/runtime evidence:** B086's P1/P2 references do not show quitting or resuming, so there is no original video evidence for this persistence path. The supplied shot-7 and B086 normal-close/resume captures establish the visible invariant (hero/world position persist), not a crash rule. For this B118 reproduction, the actual packaged normal menu callback log shows main-menu Single Player/Continue, valid 44-actor world restore, restored HP `99.1055`, then twelve saved-dead actors entering Limbus at frame 0 before the process exits with `Despawn: Spawn slot is not busy`; the crash is before the scheduled frame-1 capture. Post-fix frame captures will verify the restored game is visible and continues updating.
- **Recovered logic:** Existing B086 evidence covers `MenuBase::FS_ContinueGame` `0x420e64`, level state `0x21` (`LevelSavegame::Load`), source world identity checks, and QuickSave/Continue behavior. Existing DESPAWN2 handoff covers `CSDead::OnEvent` event 34 `0x3c4c3c`, `CSDespawn::OnBlur` `0x3c3794` (summoned actors are deleted; authored respawnable actors enter Limbus), and `CSLimbus::OnFocus` `0x3c2e58`. Source-dead `Character::Deserialize`/state reconstruction enters Limbus without replaying death End34 or the 2000 ms corpse delay. Current `SpawnPoolV1::free_all` intentionally clears transient busy/failed/summoner fields on world replacement; `main.cpp` calls it before restoring the world. `despawnTick` classifies membership (`spawnPool.owns`) as summoned, then B118's `restore_dead` hides the restored Limbus actor and unconditionally calls strict `SpawnPoolV1::release`. The exact gate is `spawn_character_v1.cpp:269`: release rejects an unbusy slot. Thus the failing actor's saved death is already represented by a free transient slot after world replacement; the restored path is incorrectly trying to release it a second time. This is independent of B116's mutable-targetable identity gate; Continue logs `status=valid` and restore succeeds.
- **Expected behavior:** Continue should restore the saved world/profile, quietly retire any source-dead summoned pool actors already represented by free post-reload slots, preserve strict duplicate/failed/unknown release errors for ordinary despawn, and keep authored respawnable actors on their Limbus/event-47 route. Minimal reusable change: provide a restore-specific slot reconciliation callback used only by `restore_dead`; it accepts an already-free owned slot as already retired and calls strict `release` for a busy owned slot. Unknown and failed slots still fail. Do not weaken `SpawnPoolV1::release` or infer pool ownership from actor HP alone.
- **Uncertainties:** There is no original quit/relaunch footage. Direct source deletion of summoned actors is clear, but the port retains predeclared pool actors and transient pool occupancy is intentionally reset, so the restore-specific cleanup must express that port representation while preserving the source-visible result. Original platform/version differences are not established.
- **Focused verification defined before coding:** helper tests cover restore of an already-free owned slot (one hide, no failure), a busy slot released exactly once, failed/unknown slot refusal, normal duplicate release still refused, and authored respawn delay unchanged. Frozen production verification repeats main-menu Continue on a fresh copy of `.local-inputs/b118/user-seed`, checks exit 0 plus absence of `Foundation error`, confirms the saved 44-actor world/profile/position restore and sees gameplay progress through captured frames, then reopens a fresh seed copy and verifies no duplicated summons/retirement errors. Compare the same accepted EXE SHA `12E7BBB69449FFACE821E7466171BD81B68F3C878750CE55BA18B18FFA3B1E5F` baseline.
