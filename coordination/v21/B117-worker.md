# B117 worker report: chest interaction crashes after movement

Owner: `/root/b117_chest_crash`; reviewer: `/root/b117_chest_review`; integration and release acceptance: root.

## Investigation before the fix

**Original visual evidence.** Reused and rechecked the original v1.0.3 P1 footage evidence in [B079 report](../v20.1/B079-report.md): chest sequence at 209.3–212.5 seconds, sampled at 15 fps in `.local-inputs/claude-v20.1/fix079/vid/d.png`. The sequence directly shows the hero crouching and extending the sword beside the chest, the lid opening, and loot rising, tumbling, and falling while the hero returns upright. This continuous sequence establishes that opening is an authored hero interaction followed by a distinct chest/loot animation; it does not establish an input-release rule. The recovered source is v1.0.2, so exact footage/source version equivalence remains uncertain.

**Original logic and current callers.** The existing B079 IDA audit identifies `CharAI::AI_InteractWith` at `0x3cff34` and `CharStateMachine::SM_SetInteractState` at `0x3c64ac`; the accepted source gates admit the live actor/OOI, interaction type, state and range before the interaction state is selected. `CSInteract::OnFocus` at `0x3c5548` requests target facing when allowed. The authored `interact` marker (467 ms in `prince_interaction.bdae`) calls the container interaction; the clip lasts 1200 ms. These are the original game rules; they do not describe the Windows frame bookkeeping that failed here.

In the Windows caller, `main.cpp`'s `ctxUseContainer` performs the actor, controller, target, action and range admission before `play_actor_clip` starts the retained Interact leaf. While `heroInteract.active`, main blocks movement/attack and zeroes the physical input at the player-control gate. In `CombatSession::update`, the locomotion action check around `combat_session.cpp:1519` then treated a still-moving `CharacterAction` as a requested Move→Idle transition and rejected it through the current authored physical-locomotion admission. This collided with retained leaf ownership: `play_actor_clip` sets `stateManaged=true`, `stateSequence=false` and clears the selected locomotion alias, while physical `select_actor_locomotion` explicitly clears `stateManaged`. The frame guard had no exception for this already-admitted authored leaf.

**Expected behavior and minimal repair.** Once an admitted retained leaf owns the actor, neutral physical input must not replace its action during that leaf. Keep the currently admitted action through the interaction, let the existing clip completion return the hero to Idle, then allow the next physical locomotion selection to publish Move normally. Preserve the authored transition guard for ordinary locomotion. The repair uses the existing retained-leaf ownership state (`stateManaged && !stateSequence`) and adds no chest, map, class, or actor special case. This ownership distinction is a host implementation detail, not a new claimed original-engine rule.

**Uncertainties.** The user-provided frame-10290 crash log identifies the live failure; no user live window was controlled. Exact source behavior still has the existing v1.0.2/v1.0.3 version caveat. B079's previously recorded item-arc/gold-bone/label-time and audible-output gaps are outside this repair. No claim is made that the internal `stateManaged` flag exists in the original engine.
