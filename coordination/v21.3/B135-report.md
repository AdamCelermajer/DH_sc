## Recovered behavior and integration diagnosis

- Original ELF identity and behavior are documented in `port/game-data/reference/player-inventory-v1/NOTES.md` and `port/game-data/reference/player-item-effects-v5/NOTES.md`. `PlayerSavegame::__LoadInventory` at `0x46a3a0` reads each item identifier, both slot bytes, quantity, value, identified byte, then ordered power count/names; it creates the real `ItemInstance` and calls `AddPower` for each saved power. It temporarily selects each equipment set for the source equip provider and restores the previous selected-set byte. Saved powers are therefore part of reconstructed item identity/properties, not a display-only decoration.
- `CharProperties::UpdateGearsProperties` at `0x3e08a8` resets the source gear sheet (`0x3defac`), calls `LoadGearsProperties` (`0x3df480`), then class recalculation (`0x3e0810`). `LoadGearsProperties` visits nine live slots; slots 1/2 use the selected set (`GetCurrentEquipSet 0x3fc6a8` via `GetEquippedItem 0x3ffe3c`), reads each ItemInstance's ordered powers (`GetNumPowers 0x3f9e80`) and loads the corresponding power entries. The port's reusable projection is `build_original_combat_properties` in `port/windows-foundation/original_combat_properties.cpp`; `OriginalEquippedItem` already accepts exact record, hand, and actual flattened power entries. Native `PlayerGearEffectsV5` resets/reprojects current set slots, source stats, powers and class calculations against the same inventory/property owner.
- The strict admission gate is `checkpoint_binding_compatible` in `DH_wt/v201int/port/windows-foundation/game_save.cpp:221–254`; it compares equipment keys, combat facts, and the complete saved/current gear sheet. `restore_game_save` validates every current binding before replacing actors/RNG/character. This gate should remain strict.
- The reproduced pre-B135 order explains the mismatch. `CombatSession::initialize` built selected equipment from definition IDs with empty power vectors, then projected profile properties. `main.cpp::initializeCombat` assigned persistent instance IDs only after the Session and combat binding already existed. The initial actor was therefore definition-only when frontend Continue reached `restore_game_save`; the strict gate correctly rejected it.
- The source metadata owner was previously created after the Continue restore block from `deathRewards.bind()`, also after restore. The frozen candidate now prepares the same owner before the first Session. The normal powered Continue is verified below; main-caller tampered metadata/expired-owner negatives remain outside this worker's receipts.

## Minimal reusable repair proposal

Keep `checkpoint_binding_compatible` unchanged. Before `CombatSession::initialize` creates a frontend player binding, make the exact same canonical metadata/power owner available and prepare a typed equipped-occurrence list in `CharacterState::equipment` order. Each entry carries stable `item_instance_id`, `definition_id`, equipment set, normalized source slot, exact `ItemRecord164`, source hand, an authentication tag, and `vector<GearPowerProperty12V5>` returned by `SourceMetadataOwnerV1::properties` for that complete current `InventoryItem`. Set 0 is the current selected-player projection supported by the current startup path; alternate set 1 remains stored and is not projected. Legacy generic `(set=-1, slot=-1)` bindings are accepted only when their textual slot is normalized by the same source-slot mapping (`slot-0`…`slot-8`, `main_hand`, `off_hand`) and that mapping is explicitly carried/checked. Metadata-present rows must resolve through the same owner. Metadata-absent rows require a positive `verified_legacy_bare` proof from the caller; absence alone never means bare. Missing, stale, wrong-instance, or malformed powered metadata fails closed; never fall back to the bare row or alter the save guard.

Add a selected-player-only input to `CombatSessionConfig` for this ordered occurrence list (prefer `vector<SelectedPlayerGearProjectionV1>` with instance/definition IDs plus `OriginalEquippedItem`). During `CombatSession::initialize`, before `build_original_combat_properties`, require exact count/order against active set-0 or normalized legacy bindings; authenticate each exact instance against both `CharacterState::equipment` and `CharacterState::inventory`; verify the ItemTable record and source hand; use occurrence indices rather than only definition strings for slots 1/2 so duplicate definitions stay distinct. Do not add a quantity admission rule without recovered source evidence. Then `build_original_combat_properties` and profile projection run as today, so source stats and saved CharacterState attributes are applied with the real gear sheet before actors are bound and before GameSave compatibility. Preserve other-set rows without counting them as active occurrences. Leave legacy non-profile diagnostic callers on their current policy.
