## Original logic and current caller path

- Recovered native source capture: `port/engine-ui/reference/character-menu-native-v1/original-functions.json` and `.asm`. `ItemInstance::GetColor()` at `0x3fa710` calls `GetNumPowers()` at `0x3f9e80`, then `GetColor(int)` at `0x3fa6dc`. `GetColor(int)` calls `GetFontDef(int)` at `0x3fa5cc`; `GetColor(int)` indexes `Arrays::FontPalette::members` and returns the row’s `textcolor` word at `+8`.
- `GetFontDef` branches on the actual power count: counts 0–4 call `PyDataConstants::getConstant("ItemPowerColor", "zero"/"one"/"two"/"three"/"four")`; count >4 returns palette row2. The authentic constants reside in `.local-inputs/windows-source-clock-v21.2/assets/data/loot_audiovisual_pycst.bin` (85 bytes, one complete group, five assignments). The exact IDs are zero=6, one=4, two=1, three=5, four=3. The actual `FontPalette` rows in `data/fonts_pyarray.bin` produce: 0=`#FFFFFF`, 1=`#9CFF9A`, 2=`#9ADEFF`, 3=`#D49AFF`, 4=`#FFE89A`, with >4 using row2=`#FFFFFF`.
- Current native callbacks that attach colored `ItemName` are `NativeInvGetEquipedItem` (`0x43d790`) and `NativeInvGetItemsListForSlot` (`0x44bb94`); both directly call `ItemInstance::GetColor()` and provide a `GetNumPowers`/instance-derived name. The latter feeds Equipment and the Merchant sell/list branch in authored `sprite251` (`port/engine-ui/reference/character-menu-flow-v1/authored-actions.json` contains both `NativeInvGetItemsListForSlot` and `NativeMerchantGetItemsListForSlot` in the merchant handler). The buy-side `NativeMerchantGetItemsListForSlot` implementation at `0x444168` is not included in the recovered character-menu function capture, so whether that separate callback uses the same native color function remains unverified; do not extend the claim to Merchant buy names without that caller trace.
- Recovered port code already has the reusable source mapping `loot::item_power_font_palette_row_v1` in `port/windows-foundation/features/loot/runtime_world_item_adapter_v1.cpp:198`, documented against the exact `loot_audiovisual_pycst.bin` mapping in `world_drop_rules_v1.hpp:76-79`. `port/level-world/item_color_lookup_v2.cpp` also implements source count-to-constant-to-palette lookup for item presentation. These are better sources for the UI row selection than a guessed color.
- The B134 private formatter API has been changed to accept `(raw_name, resolved_font_palette_row, retained_real_FontPalette, output, error)`. It preserves the raw name and resolves only that row's `textcolor`. The caller must derive the row from the same current ItemInstance using the LootAudioVisual owner (`loot::item_power_font_palette_row_v1(item.powers.size())` or equivalent source-backed lookup), then pass the row into the formatter. Do not use `MenuLocalization::borrow_text(...).localization` for `ItemPowerColor`: `MenuLocalization::load` at `port/windows-foundation/features/character_menu/menu_text.cpp:160-180` loads only `common_text_pycst.bin` and `data/fonts_pycst.bin`, where this group is absent. `dh2_script_constants_get` returns success/value0 for a missing key, which is why the former B125 callback could silently map all counts to row0/white. The current probe separately verifies that a missing source constants owner fails closed before formatting; the formatter rejects invalid palette rows without modifying the output.

## Expected behavior and minimal integration

Keep each item’s canonical raw name and source power vector unchanged. At each `ItemName` display callback, derive the palette row from that same live item’s actual `powers.size()`, resolve the textcolor from the retained authentic `FontPalette` owner, and apply it only to the display-formatted name. Counts0–4 must use the matching `ItemPowerColor` source row; counts above4 use row2. The existing `item_power_font_palette_row_v1` or `item_color_lookup_v2` can supply the row, provided the current item/owner epoch remains validated. Do not reuse `MenuLocalization`’s incomplete constant service for this table, and do not color detail descriptions, unrelated labels, sorting names, saved raw names, or payloads.

For the normal Equipment and Merchant sell-list path, wire the item-color lookup into the existing actual-instance text callback, retaining the current same-owner metadata/readiness checks and the real palette owner. Concrete low-coupling option for the integration lead: make the name-color formatter accept the **resolved palette row** plus the retained `CharacterMenuFontPaletteV1`; its caller computes that row from the actual live item’s `powers.size()` using the already source-documented `loot::item_power_font_palette_row_v1` (0→6, 1→4, 2→1, 3→5, 4→3, >4→2). This avoids reading absent constants from `MenuLocalization`. Alternatively, bind a dedicated `ItemPowerColor` callback to the genuine LootAudioVisual constants owner. The Merchant buy-side callback needs its own caller evidence before assuming the same color behavior.
