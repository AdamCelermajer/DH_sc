## Original evidence

**Visual.** I inspected the original v1.0.3 Part 1 video contact sheet `.local-inputs/claude-preview14/skills/video/sheet-766-782.png`, which is a 4×4 sampling of the relevant sequence. Its bottom-row Stats captures show one menu visit with Points Left `2 → 1 → 0` and Strength `12 → 13 → 14`; Dexterity 5, Endurance 8 and Energy 3 remain fixed. The plus buttons remain visible at zero points in the last capture. This directly establishes the successful increment sequence and visible point/stat updates. The sheet alone does not establish sound audibility; the video/audio reference in this workspace has not been auditioned, and the older POINTS report says the extracted video stream was silent. No audio claim is inferred from the stills.

**ActionScript logic and caller gates.** The retained decoded SWF action export is `port/engine-ui/reference/character-menu-flow-v1/authored-actions.txt`, under the `menu_CharacterSheetStats`/`UpdateCharInfos` action block. The four `btn_train_*` `onRelease` handlers dispatch `NativeStatsAssignPoint` with stat indices 0–3 and player 0 at offsets `0x14c95`, `0x149de`/native call `0x14a4f`, `0x14ee5`, and `0x15125`. Each source handler then calls `NativePlaySoundFX("MenuSpending", 1)` after the native mutation and before refreshing the visible stat/points values; the Dexterity sound call is at `0x14a69`. The handler's `AddedStatsThisTurn` / `useSkillPoint` condition at `0x149e9–0x14a2e` controls the pre-spend `NativeSaveGame` prefix, not whether a successful increment gets its cue (the prior B049 evidence corrects this interpretation). The native caller at `0x43eb7c` requires exactly two arguments, a valid selected property/character owner and a positive property148 before it changes a stat and debits one point. The ActionScript discards the native result, and the native callback returns void. Once a `btn_train_*` `onRelease` reaches the next statement, it emits `MenuSpending` even if NativeStatsAssignPoint returned early for zero property148. For zero points, the recovered UI code at `0x130f4–0x13179` changes each button with `gotoAndStop("deactivated")`; the action export shows the `onRelease` handlers assigned on the same button instances and no script-side `.enabled=false` or handler removal. This is evidence of a visual-state change with no explicit ActionScript release guard. The original clip sequence does not directly test a zero-points click, so native Flash hit delivery on that frame remains unobserved; do not label no-cue as original behavior from the darkened artwork alone.

The exact cue is present in `port/windows-foundation/features/audio/assets/data/sounds/sounds.xml`: `MenuSpending`, UID 0, PCM, `sfx_menu_spending.wav`, bank 6/group 4. Recovered generated Sounds bindings map the name to ordinal 146 (B122 independently checked `port/engine-audio/reference/source-bindings-v38/ledger.json`); the recovered Android runtime log at `port/android-native/reports/native-gameplay-camera-v20/17-camera-follow-movement.log` also records MenuSpending ID 97. The different numeric values are the source generated ordinal vs. platform sound ID/XML UID spaces; they are not interchangeable. The normal root audio host owns name-to-source binding and the actual V42/WinMM path. Correct in-game delivery is through `RuntimeSessionAudioV1::play_named_ui_sound`, which reproduces the `NativePlaySoundFX`/PlayMenu route; `play_named_plain` has a different source Play path and should not be used for this cue.

**Confirmation and cancellation.** The source `btnBack.onRelease` action (`0xe55b–0xe60e`) opens `menu_confirm2` with `WarningType=SettingStats` and the localized confirmation prompt when staged stat changes exist. `btn_yes.onRelease` (`0x345e1`, SettingStats branch `0x346c1–0x34825`) clears the visit flag, saves and returns to HUD; the SettingStats branch contains no `NativePlaySoundFX` call. `btn_no.onRelease` (`0x34a53`, SettingStats branch `0x34af3–0x34b5a`) reloads saved skills/stats, pops the popup and invokes the normal Back action; that branch also has no `MenuSpending` call. The source handlers therefore support one MenuSpending cue after each admitted btn_train_* onRelease that reaches the post-native sound statement; Yes/No confirmation callbacks do not replay that allocation cue. The deactivated visual frame has no explicit ActionScript input-disable assignment; native Flash hit delivery there remains unobserved. The inherited B049 report supplies the prior original video evidence for the confirm prompt and the Yes/No semantics (visible check/X at about 797–799 s), but this report does not claim a confirm/cancel sound from those frames.

**Uncertainty.** The original visual reference is v1.0.3 while recovered ActionScript/native exports and generated audio tables are from local v1.0.2 sources, with iPad v1.0.0 evidence also present. The caller and cue identity agree across available sources, but version-specific volume/output behavior and audible parity remain unmeasured. The confirm button timeline may have generic button-state sound tags outside the decoded release actions; that does not change the `MenuSpending` allocation rule and should only be added if recovered source proves it.

## Current port trace and proposed patch

The current root input route in `port/windows-foundation/main.cpp` releases the character menu through `characterMenuComposition->release(...)` at approximately line 5954. It currently calls `play_named_plain("MenuSelect")` only for returned Stats detail-page actions. Point training invokes its registered callback internally and returns `Action::none`; on successful mutation it increments `statTrainingVisit->staged_total()`. No `MenuSpending` call is present in this actual click route, so the source cue is omitted.

Minimal root-owned change: have `SourceCompositionV1::release` invoke an optional post-stat-release callback only after the presenter/hit-test/tab/provider gates have actually routed a Stats + release into its registered training callback. Invoke it after `stat_training(index, error)` regardless of the internal callback boolean, since the original ActionScript discards the void native result and continues to NativePlaySoundFX. Root binds that post-release callback to `runtimeAudio->play_named_ui_sound("MenuSpending", soundError)` and keeps existing `MenuSelect` handling separate. Confirm Yes/No do not traverse the stat-button route and have no authored MenuSpending statement. At zero points, the recovered code only calls `gotoAndStop("deactivated")`; no explicit script disable is present. Verify the actual runtime hit branch and keep native Flash input delivery qualified. The typed named-UI helper preserves exact ordinal/UID resolution, source PlayMenu gates and diagnostic distinction. Do not call this when the actual audio session is unavailable; normal verification must launch the production run with `--audio` and use the exact source asset.

A patch hunk is saved at `.local-inputs/v21.3/B121/main-callback-proposal.patch`. No shared behavior files were modified.
