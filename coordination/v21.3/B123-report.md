### Logic evidence (IDA and source caller)

- Reused `.local-inputs/ida-apk-export-2026-10-07/libraries/libDungeonHunter2.so/pseudocode-all.c`, `Character::Interact` at `0x3a4d78` (around source line 121568). Admission includes `SM_IsInteracting`/interact state, merchant classification, loot availability, valid interacting Character, and the current quest state. It obtains `Character::GetLoot`, checks merchant inventory `GetNumItems()==0`, loops the selected `MerchantTable` merchandise rows, and for each calls `ItemInventory::AddLoot(merchandise, 0, 0, -1, false)`. It then opens the merchant callbacks. Recovered port caller `port/android-native/app/src/main/cpp/source_campaign_character_interaction_v114.cpp` also resolves the actual merchant and player before the stock refill/open UI.
- `ItemInventory::AddLoot` at `0x40407c` (pseudocode lines ~188184 onward) calls `_AddLootTable` and `_AddLootItems` with inventory byte `+45`; the merchant call passes `false`, retaining weighted item selection. For each selected `LootInfo`, it applies the current-level `_Hard`/`_VeryHard` adjacent ItemTable-name rule unless bypassed, constructs an individual `ItemInstance`, maps quantity `-2` to `99`, invokes `_AddLootItemPowers` at `0x403310`, then `CalcLootItemValue` at `0x4020b4`, then `_AddItemInstance(this, item, 1, 0)` at `0x3ff5d4`.
- `_AddItemInstance` at `0x3ff5d4` tries to merge only when the item is stackable **and argument a3 is zero**; it then uses `ItemInstance::operator==`. `Character::Interact`'s `AddLoot` path at `0x40407c` calls `_AddItemInstance(this,item,1u,0)`, so a3=1 forces a fresh slot for every generated occurrence, even identical stackables. IDA `ItemInstance::operator==` at `0x3f9d78` compares ItemTable ID and ordered power IDs; it ignores value, name, and identified status. This equality applies on non-force transaction transfers (including stack/split destinations), not during merchant stock generation. Independently rolled powers can change name, color, stats, and value; power-count/selection consumes the same inventory loot RNG before later rolls.
- List caller `NativeMerchantGetItemsListForSlot` at `0x444168` fetches that actual inventory, sorts it, and emits `ItemName` from `ItemInstance::GetColor` plus the per-instance name field, `ItemIndex`, and source equippable/equipped flags. This is per-instance presentation, not a deduplicated template label.

## Expected behavior and proposed minimal reusable repair

Preserve every generated merchant occurrence as its own stock slot, including identical stackable results: merchant `AddLoot` force-appends via `_AddItemInstance(...,1,0)`. Preserve original row order, one roll for every merchandise row, source RNG consumption, quantity and difficulty-variant rules, power rolls, computed value, and per-instance localized display name/color/stats. On later non-force transaction transfer, merge only source-stackable instances satisfying original instance equality (ItemTable ID + ordered power IDs); otherwise move/append a distinct instance. Retain empty-only refill and current stock/sale/buy/reopen behavior.

Concrete patch proposal for root to apply: replace the lossy `pair<item_id,quantity>` roll result with a retained source-item payload carrying template/variant, quantity, final computed value, identified state, ordered stable power identities, and a stable occurrence identity. Derive localized name/color/stats/requirements from ItemTable + powers after generation/load; an optional display cache must not be an equality key. Route generation through `LootCreationV8` over the merchant shared session RNG, preserving one `AddLoot(...,-1,false)` call per merchandise row and the original power/value RNG draws. Carry this same payload with the item through BUY transfer into player inventory, SELL transfer into merchant buyback, buyback repurchase, and stack/split operations. The player-side representation and save/load must preserve powers, value and identified state across Continue because original `ItemInventory::TransferItemTo` moves the source instance intact and player save includes powers/value. A merchant-only ephemeral sidecar is insufficient. The exact original native pointer/object graph does not need to survive: after loading, a canonical `SourceInstanceDescriptorProvider` may rehydrate a live actual `ItemInstanceV1` + matching presentation/text owners from authentic persisted fields, but all presentation/property consumers must resolve that canonical instance and must not silently fall back to bare template data. A candidate backward-compatible storage option documented in `.local-inputs/v21.3/B123/MERCHANT-POWER.md` is an optional versioned CharacterComponent tail keyed by stable instance ID (reviewer notes the existing component envelope bounds this to 64 components × 4096 bytes); validate total payload and transaction capacity, duplicate/missing/stale instance keys, malformed/truncated/unknown records, and item-ID changes. The actual `GameSave` checkpoint Continue path also needs coverage because `game_save.cpp::character` does not serialize CharacterState components, so profile-only coverage is insufficient. Before implementation, root and integration lead must choose a compatible reusable owner and shared actual-item descriptor resolver; do not claim this bug fixed until transfer and save/reload preserve metadata and normal consumers rehydrate it. When appending/merging, use source stackability and original equality (ItemTable ID + ordered power IDs); equality ignores value/name/identified. Otherwise append distinct occurrences, including same template and same display label. Do not deduplicate by display string or template ID. Keep empty inventory as the sole refill gate.

Before integrating, complete the supplied-row identity trace by adding a scratch-only diagnostic for each original run row: merchant identity, selected table ID, merchandise-entry index/loot ID, pre/post RNG state, resulting ItemTable ID and identifier, instance ID, quantity, power count/IDs/values, computed value, and displayed name. Use the exact staged current screenshot/session seed if it can be obtained. These facts decide whether the shown same labels are duplicate templates with distinct powers, duplicate identical generated items, or a UI projection loss; no rule is guessed in advance.
