## Recovered camera and Continue logic

- Original menu caller `MenuBase::FS_ContinueGame` at `0x420e64` (IDA `pseudocode-all.c` ~208095) loads the selected profile with its saved load flag; a missing slot takes the `StartGame` branch. Existing B086 evidence covers `Level`'s saved-world admission and port frame-0 restore route. The B136 log proves this run passed the valid profile/world gates; it fails after the actual restore.
- Original camera consumer `CameraLevel::Update` at `0x410390` (~196367) calls `CameraTarget::HandleTransition` at `0x411830` (~197128). Once the transition is complete it calls `CameraTarget::GetTargetPosition` `0x411a74` and feeds that position through offset, centering, damping and camera-root updates. `CameraTarget::SetTarget` `0x4119c4` stores a nonnull target; a nonpositive duration clears transition state. `HandleTransition` queries the current destination anchor every camera frame, including the endpoint frame. The source therefore requires a live target and a current anchor at consumption time; the visual consumer is not satisfied by the restored transform alone.
- Original `GameObject::GetCameraAnchorPosition` at `0x3943b8` (~109898) returns `AnchorBase.position + c` when the actual `anchor2e0` is nonnull, otherwise the same object's `position160`. No camera height or stale authored spawn value is justified by this getter.
- Current port caller/gate in read-only `DH_wt/v201int/port/windows-foundation/main.cpp`: the source camera callback set is bound near line 3438 only when `(options.sourceCamera && !options.sourceCommands.empty()) || options.campaignTriggers`. The normal frontend arguments enable `--original-camera`, but have no camera script commands and no campaign-trigger gate, so the adapter stays unbound. The frame-0 Continue branch near line 7137 nevertheless unconditionally seeds the restored local player as the adapter target. The normal source-camera update near line 8120 then ticks any nonzero target every frame. `CampaignCameraAdapter::tick` in `port/windows-foundation/campaign_camera_adapter.cpp:56` correctly fails closed when that target has no `providers_.anchor`. This makes the observed error a caller/provider-lifecycle gap, not an invalid save or powered-item gate.
- Existing provider implementation near `main.cpp:3440–3464` already resolves the local player identity from the active `CombatSession`, source named objects through `sourceObjects`, and the player's camera anchor from the initialized actual source actor-camera owner or the current actor position. The world restore updates `options.actorPosition` from the rebound current player and resets the actor-camera owner before frame update. Reusing this provider binding for every active original-camera consumer preserves that exact-current-owner behavior. Do not add a fallback target, guessed offset, spawn-point query, or weaker tick guard.

## Expected behavior and minimal integration change

With `--original-camera`, after a valid Continue the restored player remains the target of the original gameplay camera. The first camera frame resolves that same current player's actual anchor, draws normally, and subsequent movement changes the camera anchor with the player. A world with no admitted matching save continues through the normal fresh-start path and still has a functioning current-player camera provider. Missing/stale actor bindings continue to fail closed.

Small reusable change proposal for the integration owner: bind the existing `CampaignCameraProviders` before any frame consumer whenever `options.sourceCamera || options.campaignTriggers` (or an equivalent explicit consumer-admission predicate that includes the plain original-camera update). Keep the current local-player, named-target, and anchor resolver bodies unchanged. The existing post-restore and death-revive `seed_target(player_id)` calls can then use the current provider; do not weaken `CampaignCameraAdapter::tick` or add an anchor fallback. Provider callbacks already capture the `combatSession` owner and resolve by its current player identity; confirm callback lifetime still spans any Session/world replacement in the integrated call order. Reviewer was asked to check this lifecycle detail.
