## Current production input / ownership path (read-only trace)

`main.cpp`'s live `SemanticInput::Surface.hit` returns `Control::menu_item` for any in-window point while the character menu is open, preserving the current `Presenter::hit_test` action ID. Pointer-down stores that hit and whether the menu was open; pointer-up recomputes the hit and emits a click only if both control and action match (`features/platform_input/semantic_input.cpp`, `pointer`). `replace_session_surface` clears captured pointers and pending input on gameplay session replacement; `set_menu_open` cancels captures on modal open/close. This proves mouse delivery is gated by a matching down/up hit; it does not prove the bug's click is delivered.

After a click, `main.cpp` calls `characterMenuComposition->release(...)`. The source composition first handles root tab hits. For a body click while on Equipment it invokes the registered `RuntimeEquipmentPageV1::release_for_source`. `release_for_source` rejects if a preceding source render receipt or typed inventory command remains unconsumed, then calls `release`. The page `release` first calls `ready`; `RuntimeEquipmentPageV1::Impl::current` requires the bound runtime to still use the same `CharacterState`, every inventory ID to be non-empty/unique/quantity-positive, each item to resolve through the runtime and equal the shared ItemTable row, and each optional `source_instance_current` validation to pass. `MainPage::release` routes to Details selection, equipment action, inventory category, or auto-equip banner via its authored hits. Therefore likely decision points to capture are: pointer down/up hit identity; SourceComposition root-tab selection/readiness; the per-frame Equipment provider `ready/content`; `release_for_source` outstanding-command/render-receipt admission; and `current()`'s per-row owner/ItemTable/source-resolver validation. No one has yet shown which condition fails after combat, so no cause is attributed.

One reviewed candidate is ruled out for the tested baselines: `bindEquipmentPage` builds its UI slot projection from `CharacterState.equipment_set<=0`, while `RuntimeEquipmentBindingV1::same_equipment_projection` walks every `CharacterState::equipment` binding without an equipment-set filter, which could reject duplicate source slots if alternate sets overlap. The independent baseline and normal-fight state traces both report `equipmentReady=1`, so that mismatch does not occur in those tested snapshots. A different screenshot-time save remains unexamined.

Root drains equipment pending commands and render receipts immediately after each UI click in the current production loop. Root then updates/synchronizes same-session rendering after a successful transaction. This should be verified in the actual post-combat trace before modifying it. Death/modal `SemanticInput` behavior is a separate owner: while `deathModal` is active the pointer release goes only to Death Continue; the composition is reached only after that modal state clears. This is a possible gate to trace, not evidence that stale death state caused B129.
