## Visual and source evidence

I directly inspected `.local-inputs/claude-v20.1/fix111/resume/ref-p2-386-397.png`, the sampled 1 fps sequence from original Part 2 at 386–397 s. The visible sequence moves from a dialogue/gameplay view into the Stats page, shows a point spent (Strength changes 18→20 and points left 2→0 across samples), then shows Skills and a character point-allocation confirmation. This supports the screen-transition context only; it does not establish sound identity, exact cue timing, or continuous animation. The inspected sequence does not show equipment, Faery, Quest, Map, or a back transition. Existing B111 notes cover the same reference. The decoded Actionscript is from the recovered v1.0.2 SWF while this footage is v1.0.3; parity remains uncertain.

The original caller evidence is `port/engine-ui/reference/character-menu-flow-v1/authored-actions.txt`; the source-name/UID ledger is `port/engine-audio/reference/source-bindings-v38/ledger.json`. `NativePlaySoundFX` 0x43ae10 dispatches through `VoxSoundManager::PlayMenu` 0x36bc34 to `Play` 0x36b80c, so these are plain UI PlayMenu requests. Exact bindings: MenuBack 140→UID1; MenuConfirm 141→UID2; MenuSelect 143→UID3; MenuSpending 146→UID0; MenuTab 147→UID4; PickupArmor 154→UID152; PickupPotion 156→UID153; PickupWeapon 157→UID154. B122's existing report documents the current shared `RuntimeSessionAudioV1` → `RuntimeAudioHostV1` → recovered mixer/WinMM production path and the difference between request, voice receipt, and audibility.

## Expected implementation and focused verification

Keep event routing at the actual current UI callback/pending-command boundary and use the shared named-UI API (`runtimeAudio->play_named_ui_sound("MenuTab"/"MenuBack"/"MenuConfirm"/"MenuSelect"/"MenuSpending"/"PickupWeapon"/"PickupPotion"/"PickupArmor", error)`). Preserve the original call order and source gates. The existing audio output API resolves names through the source binding and exact XML UID; do not substitute another sound when a sample or output is unavailable, and do not let audio failure veto the gameplay action. `MenuSpending` for Stats and `MenuSelect` for Stats sub-pages are already integrated; leave them single-shot.

Before implementation, focused test cases should exercise each real production event and its rejected branch: open/close and each page selection once (including repeated same-page click behavior from the authored callback); each mapped equipment slot for equip and unequip with the correct before/after cue order; Details AutoEquip and distinguish ALL-banner dispatch; skill spend with valid selected skill/points vs disabled/no-points and native refusal after an admitted callback; unlocked vs locked faery selection; transmute/drop cancel vs Yes with one cue per authored stage. Confirm no cue for ordinary row focus absent a source call. Then run the normal frozen executable with audio enabled and the accepted exact asset mount, capture UI/action logs plus cue ordinal/UID/token and started-voice receipts, and separately verify audible output before claiming audibility. This audit did not run those implementation tests or claim audio was heard.

## Uncertainties

The original video is sampled at 1 fps and the inspected SWF comes from a different recorded version (v1.0.2 vs v1.0.3). The footage does not show most of the scoped pages or any sound attribution. Main-page auto-equip ALL lacks a confirmed callback mapping here. Current page selectors and row/category inputs may adapt Flash focus/onDown/onRelease into Windows pointer releases; cue ownership must follow the actual admitted current event and document that PC mapping. The character-menu evidence concerns this bounded active UI only and does not establish a global keyboard-navigation sound policy.
