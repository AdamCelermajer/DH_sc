## Expected behavior and smallest reusable change

The authored tab callbacks request MenuTab after an admitted tab release. For the PC adaptation, submit exactly one named UI `MenuTab` after a profile-key opening event passes its existing `options.hud && combatSession` gate and opens the presenter; submit once after a pointer release returns one of `Action::{stats,equipment,skills,faery,quest,map}`. Do not emit for diagnostic direct-select options, provider selection during setup, failures that return `Action::none`, modal actions, map controls, Stats sub-page controls, or internal page callbacks. Preserve authored same-tab callback behavior: a physical click on a top tab that is admitted by the source hit-test callback should request one cue even if `select` resolves to the already-current tab. Avoid adding a second callback inside `SourceCompositionV1::select`, because it is also used by diagnostics and initial provider setup.

For the deliberate PC adaptation, `C` opens as the authored CharacterSheet tab and requests MenuTab after open. If `C` closes an already-open menu, map that admitted exit to MenuBack; Escape requests MenuBack only when the close is accepted, after modal admission. In both cases emit MenuBack immediately before the close takes effect, preserving the authored cue-before-PopAll/BackToHud ordering. Main currently installs `Presenter::close_guard` to open a stats confirmation and refuse the close when points are staged; the cue must not fire on this branch. A small reusable `Presenter::close_with_before(callback) -> bool` boundary should run `close_guard` once, invoke the callback only after admission and immediately before `open_ = false`, then return acceptance; keep `close()` delegating with an empty callback for source compatibility. If a top-page Back pointer action is included, pass the same callback through `SourceCompositionV1::release` only for `Action::close`; it must not infer acceptance from the returned enum because current release returns `close` even when the guard refuses. Do not add a cue on failed close or diagnostic teardown. Audio request failure is diagnostic only and must not veto page selection/open/close. Keep the cue API call local to the main UI input boundary; shared audio helpers, source composition, build files, and feature providers need no changes.

## Integration recipe

In root-owned `DH_wt/v201int/port/windows-foundation/main.cpp` only:

- In the admitted `uiInput.profile_pressed && options.hud && combatSession` block, after successful `characterMenu.open()` call `runtimeAudio->play_named_ui_sound("MenuTab", error)` and log ordinal/UID/token/status. On the already-open branch, call `characterMenu.close_with_before` with the MenuBack request; the callback fires immediately before close only when `close_guard` accepts.
- In the `uiInput.menu_back` branch, call `close_with_before` with the MenuBack request; the callback fires immediately before close only when `close_guard` accepts. Leave the earlier `statConfirmOpen` branch silent.
- After `characterMenuComposition->release(...)`, if and only if `releasedAction` is a top-level tab action (`stats|equipment|skills|faery|quest|map`), request one `MenuTab`. Keep this alongside the existing Stats-page `MenuSelect`, with disjoint action predicates.
- Reuse the present `runtimeAudio->play_named_ui_sound` result and status logging patterns; don't hard-code ordinal or UID and don't `continue` before the existing quest/equipment command handling. Make cue failure non-fatal.
