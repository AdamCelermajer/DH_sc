# Android 17 emulator results — 2026-10-02

The primary current-platform test used official Android 17/API 37 Google APIs x86_64 system images in separate Pixel 9 phone AVDs. No physical phone or Fold7 device was used. Both AVDs were given 4 GB RAM. The project-local SDK installation supplied Android Emulator 37.2.12, platform tools, build tools and NDK r29. See [the test plan](ANDROID-17-EMULATOR-PLAN.md) for the APK routes and source references.

## APK checks

The emulator-only signed Test 7 guest (SHA-256 `aa0628e277b7bc17aaa2273a257c3c624af52c525cdb9e606779cea42a85142a`) has `armeabi-v7a` native libraries and target SDK 24. `adb install` on each AVD returned `INSTALL_FAILED_NO_MATCHING_ABIS` with native-library extraction result `-113`. Thus its Android 9 menu behavior cannot be replayed directly on these Android 17 images.

The published Test 5 wrapper (SHA-256 `e6b81ec649e25bb32c6ec7f3f477d5ef1c2a79b7af43b7ca7643518c5f5e1b8d`) has `arm64-v8a` host libraries and target SDK 35. It installed on both AVDs with `adb install --abi arm64-v8a`, and `dumpsys package` reported `primaryCpuAbi=arm64-v8a`. On the 16 KiB image, Launch Game displayed: `This translation runtime currently requires 4096-byte memory pages. This phone reports 16384.` This is an explicit guard in the wrapper's Java source, before guest engine startup.

On the 4 KiB image, Launch Game started the plugin path, then Android's native loader reported `libnativeinterface.so is for EM_AARCH64 (183) instead of EM_X86_64 (62)` and threw `UnsatisfiedLinkError`. This happened before cache access or gameplay. Installing with `--abi arm64-v8a` did not make that plugin process accept a directly loaded AArch64 proxy. The error also occurred in the older Android 11 x86_64 diagnostic AVD. The cache was not imported for these published Test 5 wrapper checks.

## Later self-contained Test 7 package

A locally signed ARM64 package was built from the pinned Test 7 guest and exact 433,189,197-byte complete cache ZIP. Its APK SHA-256 is `85494d96aeb982025c984fadfa005b04b140b60b0e6cf96a5f90cca52e4a7c32` (446,949,980 bytes). Its APK v3 signature, ZIP CRCs and 16 KiB alignment checks passed. The game/cache inputs and generated APK remain outside Git; the build source is under `compatibility/work/fold7-build/`.

With clean app data, this package installed via `adb install --abi arm64-v8a` and unpacked its bundled cache on both Android 17 images. The launcher reported `Ready. Cache available`; 6,834 files, including one generated options file, occupied about 663 MiB of emulator storage. Launching the game still stopped at the 16 KiB page-size guard on the API 37.2 image and at the ARM64 proxy namespace mismatch on the API 37.0 x86_64 image. The complete cache is packaged and provisioned; gameplay remains unverified.

## Updated Test 7 namespace and ARM32 sysroot build

A later local Test 7 wrapper fixed the translated plugin's native-library namespace search path and bundled ARM32 sysroot aliases required by the API 37.0 emulator. Its signed APK SHA-256 is `26a5460eae8f3adb43ad8e6886a77afd08d024bfed26bbe3120324ab8269ee65` (448,470,789 bytes). It passed signature, ZIP uniqueness/CRC and alignment checks. This is a separate build from the `85494d96…` package above. The build recipe and pinned inputs are in [`STANDALONE-TEST7.md`](../compatibility/work/fold7-build/STANDALONE-TEST7.md).

On a fresh, unrooted API 37.0 x86_64 emulator with 4,096-byte pages, this APK installed with the ARM64 ABI, provisioned the bundled cache and started the original native engine. Logcat confirmed the bridged proxy, guest JNI runtime, 32 bound engine natives, Storm and shader processing. Screenshots showed the opening cinematic and Dungeon Hunter title/loading spinner. After about 272 seconds, the emulator's ARM64-to-x86_64 translation layer aborted while allocating executable translation code (`berberis::MmapImplOrDie` / `CodePool::Add`). The menu and gameplay did not appear in this Test 7 run. The 16,384-byte-page AVD remained blocked by the wrapper's page-size guard.

## Test 9 model-path and display diagnostic

The later Test 8 guest replaced one failed save-job worker branch with an existing synchronous path. Its Android 17 wrapper passed the previous translation abort and accepted a saved character at the title, then failed while reopening the prince model through a duplicated cache-root path. Test 9 adds a narrow Storm file-open retry for that exact wrapper path. The Test 9 guest and wrapper inputs are pinned in [`STANDALONE-TEST9-PATH.md`](../compatibility/work/fold7-build/STANDALONE-TEST9-PATH.md).

The clean signed Test 9 wrapper is 448,470,858 bytes, SHA-256 `5f6b31b8988231df0dc9987f656347aae940b462baed91d8e9cadb2de6eaa143`. On a fresh API 37.0 4 KiB emulator install, it unpacked the verified cache and wrote its matching completion marker. It ran the original cinematic and engine, then logged `DH2FileGuard recovered repeated root` and successfully reopened the formerly fatal prince model. On this wide emulator screen, the default viewport clipped the Start button; enabling the wrapper's **Fit game to 16:9** option produced a complete 1920×1080 character menu. Start Game and Single Player touches were accepted; loading completed and rendered a saved 3D level with the prince, an enemy, HUD and controls. A joystick drag moved the prince several tiles and shifted the camera while the guest remained alive. Pause responded, returning to the main menu updated the visible last-save time, and that timestamp persisted after a force-stop/relaunch. However, the menu cropped again after that restart even though the saved fit option was still true and the game logged a 1920×1080 surface. Enabling **Keep graphics context during cinematics** as well showed the full menu on one subsequent relaunch, without proving repeatability. Attack damage and longer-session stability remain unverified; menu layout across launches is unresolved.

## Source-built Android app

A separate signed APK built from the repository's C++ BRES, mesh, material and PVRTC modules targets SDK 37 and contains both x86_64 and ARM64 libraries with 16 KiB-aligned load segments. The exact exported APK (SHA-256 `046b4abc5f286b87b8b60af724745fe3a70bc6cc7f7fd71dbd0e4e986179c078`) installed on the API 37.2 16 KiB image, loaded the real 16,856-byte candle BRES and matching 1024×1024 PVRTC image, and rendered the textured mesh. The same path passed on the 4 KiB image using an APK whose DEX and native libraries are byte-identical; only manifest version fields changed afterward. See [`port/android-app/runtime-validation.json`](../port/android-app/runtime-validation.json) and its [build guide](../port/android-app/README.md). This is an asset renderer, not the reconstructed game.

## Reconstructed source runtime check

An independent x86_64 executable built from the reconstructed PVRTC decoder and BRES/material readers ran on the 16 KiB API 37.2 AVD. Synthetic PVRTC1 2bpp/4bpp and material/effect/sampler checks passed. The owner-supplied 1024×1024 atlas texture and 16,856-byte candle BRES also passed, with on-device SHA-256 values matching the host inputs. The executable's four load segments are 16 KiB aligned; it exited with code zero. See [`port/android-smoke/runtime-validation.json`](../port/android-smoke/runtime-validation.json) and its [reproduction steps](../port/android-smoke/README.md). This validates isolated new source components on current Android, not the original engine or a game scene.

The verified Android 17 result now includes source-built textured rendering on the 16 KiB image and short interactive original-game movement on the 4 KiB image. This is a bounded saved-level diagnostic, not full game completion or broad device compatibility. The standard Test 9 wrapper still guards against 16 KiB pages. An isolated experimental 16 KiB translator build passed guest linker/JNI/engine startup but aborted during graphics startup with a Scudo corrupted-chunk error after repeated 4 KiB-aligned `madvise` requests reached the 16 KiB kernel; it did not reach a menu. See [the page-size assessment](ANDROID-17-PAGE-SIZE-ASSESSMENT.md) and [`compatibility/16k-port`](../compatibility/16k-port/README.md). Further guest-memory and syscall work, or a complete replacement ARM64 engine, is required for 16 KiB gameplay. Renaming an ARM32 or AArch64 library does not change its machine code.
