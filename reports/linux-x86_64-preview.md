# Linux x86-64 preview port

## Investigation before implementation

This is host portability work. It does not alter combat, movement, animation, asset selection, save data, or other game rules. The visible invariant for the host layer is that the existing shared runtime presents the same authored scene, character, HUD, and input-driven updates when its window and OpenGL context come from Linux.

**Visual evidence.** I inspected the retained Preview9 capture at `.local-inputs/windows-source-clock-v19-preview-9/populated-combat-verification.ppm` (converted for inspection to `.local-inputs/linux-preview/preview9-combat.png`). It is a 1280×720 reconstructed-runtime still: the Knight is centered in the Crypt, the health/mana HUD is at the upper left, and tiled floor, stonework, and scene props remain visible around the player. This is the accepted Windows preview output, not footage from the original mobile game. A single still establishes the presentation baseline only; it cannot establish animation or input continuity. The Linux runtime check must compare a sequence of equivalent normal menu/gameplay frames and observe one input-driven transition.

**Logic evidence.** The existing host contract is `port/windows-foundation/platform_win32.hpp`: `Window` owns open/resize/poll/swap, dimensions, close/minimize/focus state, key state, client cursor coordinates, and a monotonic clock. The original Windows consumer in `platform_win32.cpp` supplies those through Win32 and a WGL context. `main.cpp` calls these services in its main loop; it uses Windows virtual-key constants and `Sleep` as host conveniences. The renderer itself is shared fixed-function OpenGL. `renderer.cpp` records the current WGL context, drawable, and thread at initialization (lines 105–129) and rejects GameObject visual-quality queries if a different context or thread is current. The reusable invariant is therefore a current compatibility-profile GL context on the drawing thread, with stable drawable identity, plus a Linux adapter for the existing Window contract. The recovered gameplay/data consumers remain the same C++ sources.

The audio consumer also has a portable boundary: `AudioOutputServices` in `features/audio/feature_audio.hpp` accepts a platform output callback around the shared `AudioMixerV34`. The Windows implementation is `WinmmAudioOutput`; the Linux implementation must pump that same mixer rather than substitute silence. `features/audio/linux-sdl2-handoff.md` records the Linux queue-clock limitation: SDL2 queued playback provides a best-available estimate from queued frames and `steady_clock`, but does not expose the hardware sample timestamp or downstream device latency available from the Windows/Android paths.

**Expected behavior.** Linux opens a resizable desktop window with a compatibility OpenGL context, maps existing host key identities to SDL input, reports dimensions/focus/minimize/cursor state, supplies monotonic seconds, swaps the same renderer output, and pumps the same audio mixer. Those are host adaptations; no game behavior is inferred or reimplemented here. The minimal implementation is the SDL2 host adapter, context/thread identity helper, stable key constants, portable sleep helper, and SDL2 audio output. The existing game/data/render queues remain the shared production implementation.

**Uncertainties.** The friend's exact Fedora release and hardware are unknown. The first WSL environment is Ubuntu 26.04 with glibc 2.43, which is too recent to choose as the release baseline without a known Fedora version. A private Ubuntu 22.04 (glibc 2.35) toolchain is being prepared. Fedora compatibility will be stated from the final ELF's required `GLIBC_*` and `GLIBCXX_*` symbol versions, not inferred from the distro name. Xvfb/llvmpipe can verify context creation and rendering in this environment but cannot establish friend-hardware acceleration, display integration, or audio latency.

**Focused verification.** Before host code, the planned checks were: build a private SDL2/OpenGL probe; under Xvfb, create a compatibility context, query GL/context/drawable/thread identities, resize and poll the window, draw and swap a frame; then build the actual shared Linux game target and observe its menu/gameplay frames plus movement input in an isolated runtime profile. Audio gets separate dummy-driver queue, focus, reopen, and unavailable-device checks. No user window or save is part of this test.

## Work and verification status

- Added `platform_linux.cpp`, a Linux implementation of the existing Window interface, plus `platform_context_identity.{hpp,cpp}`, `platform_key_codes.hpp`, and `platform_sleep.hpp`.
- A private CMake probe compiles the new Linux host files under two sysroots. With SDL2 2.32.10, Ubuntu 26.04, Xvfb, and Mesa llvmpipe it opened a 640×480 window, created an OpenGL 4.5 compatibility context, confirmed nonzero context/drawable/thread identities, resized to 800×600, cleared and swapped a frame, and exited successfully. Receipt: `OpenGL 4.5 (Compatibility Profile) Mesa 26.0.8-1ubuntu0.3 / llvmpipe (LLVM 21.1.8, 256 bits) / 800x600`. The same probe passed inside a private Ubuntu 22.04 chroot with SDL2 2.0.20 and Mesa 23.2.1: `OpenGL 4.5 (Compatibility Profile) Mesa 23.2.1-1ubuntu3.1~22.04.4 / llvmpipe (LLVM 15.0.7, 256 bits) / 800x600`. That binary requests GLIBC 2.34 and GLIBCXX 3.4.21; full-game requirements remain to be checked from the final ELF.
- A second private Xvfb probe sent an actual X11 W keydown through xdotool; the SDL `Window::poll`/`key_down('W')` path observed it while the window was focused. Receipt: `SDL key pump observed W; focus=1`. This verifies the adapter's key mapping without opening or controlling the user's game window.
- The separate SDL2 audio worker built its backend against the existing mixer and passed dummy-device render/queue/clock/focus/close/reopen and unavailable-device checks. The clock limitation above remains.
- Main/CMake/renderer integration and a full game ELF are pending the Windows movement hotfix freeze and integration-lead review. No production menu, combat, movement, or visual parity claim is made yet. Preview9 remains the release baseline.
